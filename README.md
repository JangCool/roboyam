# Claude Code 기능 단위 개발 가이드

## 목표

스토리보드를 별도로 만들지 않고, 실제 프론트엔드 화면을 기획·검토·확정의 기준으로 사용한다. 확정한 기능을 백엔드와 연결하고, 사용자가 요청한 경우에만 QA를 진행한다.

이 가이드는 Claude Code의 실제 설정 형식을 기준으로 만든 시작 템플릿이다. 프로젝트의 기존 설정·기술 스택을 확인한 후 적용한다.

## 권장 개발 흐름

1. **요구사항 협의**: 메인 Claude가 요청을 분석한다. 막히는 정책만 질문하고, 상세 기획서나 스토리보드를 만들지 않는다.
2. **프론트엔드 구현**: 화면 중심 기능이면 목업 데이터로 실제 화면과 상호작용을 구현한다.
3. **개발자 확인**: 개발자가 브라우저에서 확인한다. 피드백이 있으면 프론트엔드만 수정한다.
4. **화면 확정**: 사용자가 확정 의사를 밝히기 전에는 백엔드 구현을 시작하지 않는다.
5. **백엔드 구현**: 확정된 UI와 업무 규칙을 기준으로 API·검증·권한·DB 로직을 구현한다.
6. **연동**: 프론트엔드 목업 호출을 실제 API로 교체한다.
7. **QA**: 사용자가 요청한 경우에만 시나리오를 작성하고 관련 테스트를 선별한다.

```text
요구사항 협의
    ↓
Frontend Agent + mock data
    ↓
개발자 브라우저 확인 ── 수정 요청 ──→ Frontend Agent
    ↓ 화면 확정
Backend Agent
    ↓
Frontend Agent 또는 메인 Claude가 API 연결
    ↓
사용자 요청 시 QA Agent
```

## 프론트엔드 우선이 적합한 경우

- 백오피스 CRUD, 목록·검색·필터, 상세보기, 상태 변경
- 화면을 실제로 사용해보면 업무 요구사항이 구체화되는 기능
- 사용자 흐름과 정보 배치가 핵심인 기능

## 백엔드/정책 우선이 적합한 경우

- 결제·환불·정산처럼 상태 전이와 데이터 정합성이 핵심인 기능
- 인증·권한·보안 정책, 데이터 마이그레이션
- 배치, 집계, 대량 처리, 외부 시스템 연동

이런 기능은 UI를 먼저 그려도 핵심 규칙이 결정되지 않으므로 정책과 데이터 흐름을 먼저 협의한다. 필요하면 UI 프로토타입은 병행하되, UI만 보고 서버 규칙을 추측하지 않는다.

## 권장 파일 구조

```text
project/
├── CLAUDE.md
├── .claude/
│   ├── agents/
│   │   ├── frontend-developer.md
│   │   ├── backend-developer.md
│   │   └── qa-reviewer.md
│   └── skills/
│       ├── feature-flow/SKILL.md
│       └── targeted-qa/SKILL.md
└── docs/
    └── domain/
        └── TEMPLATE.md
```

- `CLAUDE.md`: 모든 작업에 필요한 핵심 규칙만 둔다.
- `agents/`: 실제 위임이 필요한 프론트엔드·백엔드·QA 작업자만 정의한다.
- `skills/`: 반복 워크플로를 명시적으로 호출할 수 있도록 정의한다.
- `docs/domain/`: 회원·광고·게시판 등 실제 프로젝트의 업무 정책을 보관한다. 관련 도메인 문서만 필요할 때 읽는다.

기획 에이전트는 별도로 만들지 않는다. 작은 기능의 요구사항 협의는 메인 대화에서 처리해 에이전트 호출 및 컨텍스트 전달 비용을 줄인다. 도메인별 에이전트도 처음부터 모두 만들지 말고, 공통 백엔드 에이전트로 부족해지는 업무가 확인된 뒤 추가한다.

## 스토리보드 대신 남길 최소 정보

대부분의 UI 중심 기능은 실제 구현 화면을 기준으로 삼고 별도의 스토리보드를 만들지 않는다. 백엔드로 넘길 때 메인 대화에서 다음 항목을 짧게 요약한다.

- 확정한 화면과 사용자 동작
- 입력 필드 및 검증 규칙
- 권한·상태 전이 등 확정된 업무 규칙
- 화면에서 필요로 하는 데이터와 API 후보
- 아직 미확정인 사항

이 요약은 보통 대화 안에서 전달한다. 여러 세션에 걸쳐 작업하거나 복잡한 계약을 추적해야 할 때만 `docs/features/<기능명>-contract.md` 같은 파일로 저장한다. 이는 스토리보드가 아니라 프론트엔드와 백엔드 사이의 최소 계약이다.

## 테스트 운영 원칙

- 구현 중 자동으로 전체 테스트, E2E, 전체 회귀 테스트를 실행하지 않는다.
- 개발 중 반드시 필요한 최소 컴파일·타입 검사만 허용한다. 저장소를 확인하기 전에는 명령어를 추측하지 않는다.
- `시나리오만 작성해줘`는 체크리스트만 작성하고 테스트 명령을 실행하지 않는다.
- `QA 실행해줘`처럼 실행을 명시적으로 요청받은 경우에만 연관된 테스트를 선별한다.
- 관련 테스트가 없으면 전체 테스트로 대체하지 않는다. 미보유 테스트와 검증 한계를 보고한다.
- 최종 전체 회귀 테스트는 사용자가 범위를 명시적으로 요청한 경우에만 검토한다.
- 화면 디자인·레이아웃 리뷰는 개발자가 직접 한다. QA 에이전트는 브라우저 시각 리뷰를 수행하지 않는다.

## 제한 사항과 강제 제어

`CLAUDE.md`, 에이전트 프롬프트, Skill 지침은 모델 행동을 유도하는 지침이지 강제 보안 경계가 아니다. 테스트 명령 실행을 기술적으로 차단해야 한다면 실제 저장소의 테스트 명령, 셸, 운영체제, QA 승인 방식을 파악한 뒤 `PreToolUse` 훅 등을 별도로 설계한다. 프로젝트 확인 전부터 모든 테스트 명령을 무조건 차단하는 설정은 승인된 QA까지 막을 수 있어 기본 템플릿에 포함하지 않았다.

## 시작 방법

1. 이 폴더 안의 파일을 프로젝트 루트에 복사한다. 기존 `CLAUDE.md`나 `.claude` 파일이 있으면 덮어쓰지 말고 내용을 비교해 병합한다.
2. Claude Code에서 `/feature-flow 광고 관리의 일시정지 기능`처럼 호출한다.
3. 화면을 확인하고 수정할 때는 일반 대화로 피드백을 전달하거나 `/feature-flow 화면 수정: ...`을 호출한다.
4. 화면 확정 후 `/feature-flow 화면 확정, 백엔드 진행`을 호출한다.
5. 백엔드 연동 후 시나리오만 필요한 경우 `/targeted-qa 시나리오만 작성: 광고 일시정지`, 테스트 실행을 원하는 경우 `/targeted-qa QA 실행: 광고 일시정지`를 호출한다.

새 `.claude/agents/` 디렉터리를 현재 실행 세션 중 처음 만들었다면 해당 세션을 재시작해야 에이전트가 감지될 수 있다.
