# 운영자 · 역할 · 권한

> 사용자에게 확정받은 정책만 "확정"에 적는다. community·hamonica3 에서 확인한 사실은 "참고"에 따로 적고, 정하지 않은 것은 "미확정"에 둔다. (작성 2026-10-21, 서버 코드는 아직 이 정책대로 바뀌지 않았다. 화면 목업과 API 후보는 `docs/features/roles-contract.md`)

## 책임 범위
- **운영자**(관리자 앱에 로그인하는 계정)와 그 역할·권한, **게시판 관리자·게시판 스텝**(게시판별로 지정하는 일반 회원)의 경계를 정한다.
- 회원 등급·제재·게시판 읽기/쓰기 권한은 **회원 도메인**이다. 이 문서는 운영자 쪽과 게시판 관리자·스텝 지정만 다룬다.

## 핵심 개념
| 구분 | 누구 | 계정 | 일하는 곳 |
|---|---|---|---|
| 회원 | 공개 사이트 이용자 | `users` | 공개 사이트 |
| 운영자 | 관리자 앱 사용자 | `operators` (**`users` 와 별도 테이블**) | **관리자 앱에서만** |
| 게시판 관리자(매니저) · 게시판 스텝 | 게시판 하나를 맡은 **일반 회원** | `users` + 게시판별 지정 | 공개 사이트(그 게시판 안에서만) |

- 운영자는 회원이 아니다. 운영자 권한과 회원 권한은 서로 다른 체계다.
- 용어: 운영자 = 관리자 앱 계정 전체. 그중 **최고 관리자** 1명(루트)과 **직무 역할**을 받은 운영자로 나뉜다. 기존 `STAFF`("운영진") 개념은 직무 역할로 대체한다.

## 확정된 업무 규칙
1. **계정 분리**: 운영자 계정은 `operators` 별도 테이블이다. 회원 `users` 에는 운영자 역할(`STAFF`·`ADMIN`)을 두지 않는다.
2. **운영 조치는 관리자 앱에서만** 한다. 운영자는 공개 사이트에서 운영 권한으로 일하지 않는다.
3. **역할은 여러 개 합집합**(community 방식): 운영자 한 명에게 직무 역할 여러 개를 줄 수 있고, 권한은 모두 합친다. 개인별 예외 권한은 두지 않고 역할을 새로 만들어 준다.
4. **최고 관리자는 루트 계정 1명**(설치 마법사가 만든다). 다른 운영자에게는 권한 설정으로 "최고 관리자에 가까운 역할"을 만들어 줄 수 있다. 최고 관리자 자리를 늘리지는 않는다.
5. **운영자 등록은 두 방식 모두 제공**한다: ① 최고 관리자(또는 권한 있는 운영자)가 계정을 만들거나 초대한다. ② 운영자 신청을 받아 승인한다.
6. **계정 상태는 hamonica3 방식**: 승인·잠금·만료·사용 4개 상태와 계정 기간. 로그인은 *승인됨 · 잠기지 않음 · 사용 중 · 기간 안*일 때만 된다.
7. **업무 영역별로 역할의 유형을 구분**한다(공동구매·핫딜·광고 등 업무가 다른 메뉴가 있다). 역할은 유형에 맞게 만들고, 유형에 속한 권한만 고르게 한다.
8. **게시판마다 매니저와 스텝을 지정**할 수 있다(게시판을 만들 때 또는 이후). 둘 다 **일반 회원으로 지정 가능**하다. 세부는 아래 "게시판 매니저·스텝".
9. **스텝은 일반 회원이므로 글 삭제·댓글 삭제 등의 횟수에 제한을 둔다**(community "지킴이" 값 기준). 세부는 아래 "게시판 매니저·스텝".

## 게시판 매니저 · 스텝 (결정 2026-10-21 — 일반 커뮤니티 조사 + community 지킴이 값 기준, 사용자 위임 결정)
**조사 요약**: 네이버 카페는 개별 게시판 스탭이 담당 게시판에서만 글 삭제·이동, 댓글 삭제, 활동정지를 할 수 있고 타인이 건 정지는 풀 수 없으며 삭제물 복구는 본인 것만 가능하다. 스탭 임명·게시판 추가/제거는 매니저 몫이다. 다음 카페의 게시판지기는 남의 글 삭제를 못 한다. XenForo 는 포럼별 모더레이터가 지정된 포럼 안에서만 권한을 쓰고 관리자와 별개 역할이다. 디시인사이드는 매니저가 삭제한 글의 처리자를 알 수 없어 남용을 못 가린다는 문제가 있다. 공통 패턴: **매니저 = 게시판 책임자(스텝 지정·공지·복구), 스텝 = 처리 담당(범위·횟수 제한, 타인 처리 복구 불가), 모든 처리는 처리자 기록**.

| | 게시판 스텝 | 게시판 매니저 |
|---|---|---|
| 정체 | 일반 회원 + 그 게시판 지정 | 일반 회원 + 그 게시판 지정 |
| 글 숨기기·삭제, 댓글 삭제, 게시판 한정 제재(경고·쓰기 제한 1/3/7일) | 가능 (한도 안에서, 사유 필수) | 가능 (스텝과 **같은 한도 기본값**, 운영자가 매니저 개인별로 올릴 수 있다) |
| 그 게시판 공지·고정 | 불가 | **가능** |
| 그 게시판 스텝 지정·해제 | 불가 | **가능** (자격은 시스템이 검증, 매니저 지정은 불가) |
| 스텝 처리 복구·처리 내역 열람(처리자 포함) | 본인 처리 내역만 | **자기 게시판 전체 열람, 스텝 처리 복구 가능** |
| 사이트 제재(정지·영구 정지), 게시판 설정·삭제, 신고 처리, 이의제기 판단, 다른 게시판 | 불가 | **불가**(운영자 전용) |
| 관리자 앱 로그인 | 불가 | 불가 |

- **지정 주체**: 매니저는 운영자(권한 `게시판 구성` 처리)만 지정·해임한다. 스텝은 운영자 또는 그 게시판 매니저가 지정·해제한다. 게시판을 만들 때 함께 지정할 수 있다.
- **인원**: **매니저는 게시판당 기본 3명, 설정으로 최대 10명까지**(확정, 사용자 지정). 스텝은 게시판당 최대 10명(community 값)이고 매니저와 따로 센다(합산 상한 없음). 한 회원이 맡을 수 있는 게시판은 최대 5개(community 값, 매니저·스텝 합산).
- **지정 자격**(community 기준): 회원 상태 정상, 이메일 인증 완료, 등급 일반 이상(새싹 불가), 사업자 계정 불가, 탈퇴·정지 불가. 핫딜·직접홍보·소모임 게시판은 지정 불가(해당 기능이 생길 때 적용).
- **자동 해제**: 새싹으로 강등 / 기간·영구 정지 시작 / 탈퇴 / 사업자 전환 시 그 회원의 모든 게시판 지정이 끝난다. 정지가 풀리거나 등급이 오르거나 휴면 전환돼도 자동 복귀·해제는 없다. 처리할 때마다 자격을 다시 판정한다.
- **하루 한도**(community 기본값·범위): 글 숨기기+삭제 합산 10(1~50), 댓글 삭제 20(1~100), 제재(경고+쓰기 제한) 합산 5(1~20). 값은 게시판 기본값 → 게시판별 → 개인별 순으로 덮어쓴다(비면 상위 값). 하루는 한국 시간 0시 기준, 같은 날 해제 후 재지정해도 횟수는 이어진다. 되돌려도 한도는 복구되지 않는다. 한도를 0으로 막는 값은 없다(막으려면 해제). 초과하면 거절하고 남은 횟수·초기화 시각을 알려 준다.
- **처리 규칙**: 사유 필수, 코드 선택(스팸·광고 / 비방·인신공격 / 투자 권유 / 게시판 주제 불일치 / 기타 — `기타`는 제재에만). 처리 불가 대상: 공지·고정 글, 운영자 작성물, 같은 게시판의 다른 스텝·매니저, 소모임 글, 본인. 이미 쓰기 제한 중인 회원에게 쓰기 제한을 더 주는 것은 불가(경고는 가능).
- **반복 제재 검토**: 같은 회원이 같은 게시판에서 최근 7일에 제재 3건 이상(경고·쓰기 제한 합산, 처리자가 달라도 합산)이면 운영자 검토 건이 열린다. 운영자가 `그대로 둠` 또는 `사이트 제재 부여`로 닫는다.
- **쓰기 제한 효력**: 그 게시판의 새 글·댓글·답글·임시저장이 막힌다. 읽기·추천·수정·삭제·쪽지·다른 게시판은 그대로다. 사이트 제재와 따로 센다. 이의제기는 기존 흐름을 재사용하고 인용되면 즉시 풀린다.
- **공개 사이트 표시**: 지킴이 표시·처리자 표시를 일반 회원에게 노출하지 않는다. 숨김·삭제된 글은 작성자 포함 모두에게 보이지 않는다. 처리자 신원은 운영자·그 게시판 매니저 화면에서만 본다. 알림은 처리 종류별로 사유와 함께 보내고 끌 수 없다. 이메일은 사이트 제재에만 보낸다.
- **기록**: 지정·해제(누가·언제·종료 사유), 한도 변경, 처리 내역(처리자·사유·대상)을 남기고 감사 로그와 연결한다. 처리 기록 보관 기간은 미확정.
- **운영자 권한 연결**: 지정·한도·해임은 `콘텐츠 > 게시판 구성`, 처리 감독·복구·반복 제재 검토는 `커뮤니티 안전 > 스텝 처리 감독`·`제재·이의제기` 유형이다.

## 참고 (확인된 사실 — 결정 아님)
- **hamonica3**: `role`·`permission`·`role_permission` 3표. 권한 목록은 코드(enum, `영역.행위`)가 원천이고 서버가 뜰 때 DB와 맞춘다. `@RequirePermission` + 인터셉터가 **선언 없는 API를 거절**한다(fail-closed). 마지막 활성 최고 관리자는 잠글 수 없고, 내장 역할은 삭제할 수 없다. 권한 변경은 감사 로그에 `granted/revoked` 로 남는다.
- **community**: 직무 역할(`staff_roles`)에 **메뉴별 단계(없음/읽기/쓰기)** 와 **조치 권한**(환불 승인·CSV 내보내기·재고/가격 변경 등)을 준다. 업무 영역 키: 신고·제재·이의제기·후기·금칙어 / 회원·닉네임 이미지·사업자 / 공지·글·하이라이트 / 핫딜·공동구매 주문·상거래(딜·주문·정산) / 프로모션·광고. 관리자 앱 로그인과 세션은 공개 사이트와 분리(`ADMIN_SESSION`, 비활동 2시간·최대 12시간). 서버가 요청마다 현재 상태를 다시 읽는다.
- **community 의 약점**(피한다): 권한 검사가 흩어져 새 컨트롤러에 검사를 빼먹으면 운영진이 통과한다 / 공개 사이트에서 운영진이 쓰는 즉시 조치가 메뉴 단계를 보지 않고 관리자 앱 세션 정책도 거치지 않는다 / `users.role` 에 여러 신분을 끼워 넣어 "USER 만" 가정이 퍼졌다.
- **community 지킴이**(게시판 스텝 참고): ADMIN 이 게시판마다 지정(대상: USER · 일반 등급 이상 · ACTIVE · 이메일 인증). 할 수 있는 일은 그 게시판 안의 글 숨기기·삭제, 댓글 삭제, 게시판 한정 제재(경고·쓰기 제한 1·3·7일). **하루 한도 기본 글 10 / 댓글 20 / 제재 5**(서버가 센다). 새싹 강등·정지·탈퇴·사업자 전환·운영진 지정 시 자동 해제. 처리 내역은 별도 기록하고 처리자 신원은 공개 API 에 내보내지 않는다. 기능 스위치 `community.keeper.enabled` 기본 false.

## 역할 유형 (확정 2026-10-21 — 분류는 이대로, 권한 코드는 기능이 정해질 때)
역할은 **영역(대분류) → 유형(세부)** 두 단계로 나눈다. 유형은 그 역할이 고를 수 있는 **권한 후보 묶음**이다(역할을 만들 때 유형을 하나 고르면 그 유형의 권한만 보인다). 각 유형의 권한은 `조회`(보기) · `처리`(승인·삭제·상태 변경 같은 업무) · `설정`(규칙·구성 변경)으로 나누고, 되돌리기 어려운 일은 **민감 조치**로 따로 둔다. community 는 설정 화면을 최고 관리자 전용으로 잠갔지만, 여기서는 "최고 관리자에 가까운 역할"이 가능해야 하므로 `설정`도 권한으로 위임할 수 있게 한다. 기능이 아직 없는 유형은 목록에만 있고 화면에는 나오지 않는다. 권한 코드(`영역.행위`)는 기능이 정해질 때 확정한다.

| 영역 | 유형 | 다루는 일 (community 메뉴 근거) | 설정 권한 예 | 민감 조치 예 |
|---|---|---|---|---|
| 콘텐츠 | 공지·주요글 | 공지, 하이라이트, 인기글 노출·제외, 예약 글 | 인기글 점수식, 예약 보관 | — |
| | 게시글 | 글 검색·숨김·삭제·이동 | — | 글 일괄 삭제 |
| | 게시판 구성 | 게시판·말머리 만들기/순서/켜고 끄기, 글쓰기 등급·작성 속도·노출 기본값, 게시물 종류·19금 규칙, **게시판 매니저·스텝 지정과 한도** | 게시판 기본값, 스텝 한도 | 게시판 삭제 |
| | 사이트 화면 구성 | 공개 사이트 메뉴, 홈 레이아웃·가젯 | 전부 설정 | — |

| | 금칙어 | 금칙어 보기·테스트·변경 | 금칙어 사전 | — |

- 커머스 권한(`docs/domain/commerce.md` 13-2, `commerce-foundation-contract.md` 결정 12)의 유형: `shop.*`·`point.adjust.large`·`point.refund.*` = 등급·포인트·휴면, `commerce.groupbuy.cancel`·`commerce.refund.large` = 주문·배송, `commerce.payment.read`·`commerce.reconcile.manage` = 정산·증빙. 0-5 에서 코드로 더했고 그 기능이 생기기 전까지 「기능 준비 중」(`featureReady=false`)이다. 고액 권한은 시드 역할에 넣지 않고 최고 관리자가 골라 준다.

- 역할 하나는 유형 하나에 속하고, 운영자에게는 여러 역할을 줄 수 있다(합집합). "공구 담당"은 `상품·공구 기획` + `주문·배송` 역할 둘을 주는 식이다.
- **역할을 만들고 고치는 권한(운영자·역할 관리)은 최고 관리자에게만 기본 부여**한다. 이 유형의 역할을 받은 운영자도 **자기가 가진 권한 범위 안에서만** 다른 운영자·역할에 부여할 수 있다(권한 상승 방지, 확정).
- **게시판 매니저·스텝은 이 표의 역할이 아니다**(회원 + 게시판별 지정). 단 **지정과 한도 설정**은 운영자 권한(`게시판 구성`)이다.

## 회원 역할 (제안 — 확인 전, 2026-10-21)
역할은 **두 축**이다(hamonica3 의 시스템/워크스페이스 축에 해당): **운영자 역할**(위 표, 관리자 앱 권한)과 **회원 역할**(공개 사이트 회원의 유형별 능력). 운영자 권한과 회원 권한은 서로 다른 체계다(확정). 역할 관리는 메뉴가 종류를 나눈다(확정 2026-10-21): **회원 역할 · 운영자 역할 · 등급 역할** 세 하위 메뉴(등급 역할은 회원 역할의 한 종류)이고, 한 화면 안에서 운영자/회원을 다시 나누지 않는다. 화면 구조는 `docs/features/roles-contract.md`.

| 회원 역할 유형 | 내장 역할 | 부여 방식 | 비고 |
|---|---|---|---|
| 등급 | 새싹 · 일반 · 단골 · 베테랑 (**현재 4단계, 추후 확장 가능 — 등급은 순서 있는 목록이며 등급 설정이 원천이고 등급 역할은 거기서 자동 생성되는 파생물. **최대 10단계. 등급을 삭제하면 소속 회원은 바로 아래 등급으로 이동**, 확정 2026-10-21) | **자동 승급**(확정 2026-10-21): 글·댓글 수처럼 **사건으로 판정 가능한 조건은 즉시**, 가입 일수처럼 **시간 경과가 필요한 조건은 배치**로 판정. 기준을 낮추면 **소급 승급**. **운영자가 수동으로 올린 회원에게만** 적용되는 **설정 옵션**(전역 1개: 계속 자동 승급 / 자동 승급 중지)이 이후 자동 승급을 정한다. 수동으로 올린 적 없는 회원은 이 옵션과 무관하게 일반 자동 승급 규칙을 따른다 | 등급 기준(가입 일수·글·댓글 수)·옵션은 `회원 > 등급·포인트·휴면` 설정(등급 설정 화면) |
| 회원 유형 | **일반 회원**(가입 시 기본), **사업자 회원** | 가입·사업자 승인 시 자동 | 사업자는 읽기·프로필·허용 게시판만(community 기준) |
| 게시판 단위 | **게시판 매니저 · 게시판 스텝** | 게시판별 지정(위 "게시판 매니저·스텝") | 범위 = 게시판 하나. 한도·권한은 그 섹션 규칙 |
| 사용자 정의 | (운영자가 직접 추가) | 운영자가 회원에게 수동 부여 | 예: 베타 테스터, 우수 회원 |

- 회원 역할의 **권한은 사이트 전체 능력 단위**다: 글 쓰기, 댓글 쓰기, 쪽지 보내기, 파일 첨부, 추천·신고, 닉네임 이미지 신청, 포인트 상점 이용 등. 게시판별 최소 등급 같은 **게시판 규칙은 게시판 설정에 그대로 두고**, 역할 권한과 게시판 규칙을 **둘 다 만족해야** 한다(안). 정지·영구 정지는 역할이 아니라 **상태에 따른 제한**(읽기만 / 이의제기만)이다.
- 아직 사이트 기능이 없는 권한(소모임 개설, 핫딜 등록, 공동구매 구매, 광고 신청 등)은 목록에만 두고 "준비 중"으로 비활성이다.
- 한 회원은 역할 여러 개를 가진다(등급 1 + 회원 유형 1 + 게시판 지정 0~N + 사용자 정의 0~N). 효력은 합집합.
- 회원 역할을 만들고 고치는 권한은 운영자 권한 `role.manage` 를 쓴다(권한 상승 방지 규칙은 회원 쪽에는 해당 없음 — 안).

## 이 정책이 바꾸는 현재 코드
- `server/shared` 의 `Role` enum(`USER·STAFF·ADMIN`)과 `users.role` CHECK(`V2__auth.sql`): 운영자 값 제거.
- 설치 마법사의 루트 계정 생성(지금은 `users` 에 ADMIN): `operators` 에 최고 관리자로 만든다.
- 공개 `GET /api/auth/me` 의 `adminUrl`(`docs/features/login-contract.md`): 운영자는 공개 사이트에 로그인하지 않으므로 없앤다.
- `AuthUser`(`ROLE_USER·ROLE_STAFF·ROLE_ADMIN`)·`SecurityConfig`: 관리자 서버(`server/admin`)는 `operators` 기준 인증으로 분리한다.
- admin-web 의 `AdminRole('ADMIN'|'STAFF')`·`RoleBadge`·목업 로그인: 최고 관리자/직무 역할 표시로 바뀐다.

## 추가 확정 (2026-10-21, 사용자 선택)
- **운영자 초대**: 1회용 **초대 링크**를 이메일로 보내 본인이 비밀번호를 설정한다(유효기간 기본 72시간 — 가정, 값은 구현 때 조정 가능). 운영자 신청 후 승인 방식도 함께 제공한다.
- **운영자 로그인 보안**: community 기준 — 세션 비활동 2시간·최대 12시간, 로그인 실패 5회 시 잠금(해제 방식·자동 해제 시간은 구현 때 가정을 명시). 비밀번호 규칙은 공개 사이트와 같다.
- **감사 범위**: 역할·권한·운영자 상태 변경 + 로그인 성공/실패 + 권한 거부를 기록한다. 보관 기간은 1년(가정).
- **회원 역할**: 아래 "회원 역할" 제안을 그대로 확정한다(두 축, 유형 4종, 권한은 사이트 전체 능력 단위, 역할 권한과 게시판 규칙 **둘 다 만족**, 등급 역할 자동 부여 + 게시판 최소 등급 병행).

## 미확정 사항 (정해야 구현할 수 있다)
> 아래 6·7·8·10번은 위 "추가 확정"으로 큰 방향이 정해졌다. 남은 세부(신청 항목·승인자 권한, 잠금 해제 방식, 비밀번호 재설정, 계정 기간 사용 여부, `member.pii`)만 구현 때 가정을 명시한다.
1. **게시판 매니저·스텝**: 위 결정을 사용자가 검토 전이다. 특히 매니저의 스텝 지정·공지·복구 권한, 매니저 한도를 스텝과 같게 둔 것. (매니저 수는 기본 3명·최대 10명으로 확정. 이 값을 게시판별로 정하는 위치(게시판 기본값 + 게시판별 덮어쓰기)는 게시판 기능 구현 때 정한다.)
2. **게시판 스텝 기능의 시점**: 게시판·글·댓글·제재 기능이 만들어질 때 함께 구현한다(지금 범위 밖). 처리 기록 보관 기간, 인원 상한·반복 검토 기준(10명·5게시판·7일 3건)을 설정으로 열지 코드 상수로 둘지.
5. 역할 유형 분류는 확정. 권한 코드(`영역.행위`)는 영역별 기능이 정해질 때 함께 확정한다.
6. **운영자 등록 세부**: 초대 방식(링크·임시 비밀번호)과 유효기간, 신청 때 받는 항목과 이메일 인증, 승인자(어떤 권한), 운영자 계정 기간(만료)을 쓸지.
7. **로그인 보안**: 운영자 로그인 실패 잠금 기준, 세션 시간, 비밀번호 규칙, 운영자 비밀번호 재설정 방식.
8. **감사 범위**: 권한·역할·운영자 상태 변경과 로그인 성공·실패, 권한 거부를 기록하는 범위·보관 기간.
9. 최고 관리자(루트)의 비밀번호 분실·계정 보호 절차.
11. **등급 승급(확정 부분 제외 남은 것)**: 가입 일수 배치의 실행 주기·시각(하루 한 번 가정), 수동 상향 옵션의 정확한 값(현재 구현 가정: `계속 자동 승급` / `자동 승급 중지` 두 가지 — "수동 승급 표시"를 별도 값으로 둘지), 소급 승급 시 알림·이력 방식, 활동 수(글·댓글)의 정의(삭제·숨김 제외 등).
10. **회원 역할**: 위 제안(두 축, 유형 4종, 권한 단위, 게시판 규칙과 둘 다 만족)이 맞는지. 등급 역할 자동 부여와 등급별 능력 차이를 역할 권한으로 둘지 게시판별 최소 등급으로만 둘지. 회원 조회의 이메일 마스킹 기본 적용과 해제 권한(`member.pii`).
