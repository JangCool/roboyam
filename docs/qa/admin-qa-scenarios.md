# 관리자 사이트 QA 시나리오 (2026-11-16)

> 사용자 요청: 관리자 화면에서 **공개 사이트 설정 항목 전부**를 주로 시험하고, 관리자 사이트 전체를 **운영자 계정·역할 권한별**로 시험한다. 에이전트가 사용자의 Chrome(Claude in Chrome)으로 직접 확인하고, 버그·오작동은 고친 뒤 다시 확인한다. 성능도 함께 잰다.

## 0. 범위와 우선순위
| 순위 | 묶음 | 내용 |
|---|---|---|
| **P0** | A. 공개 사이트 설정 | 관리자에서 바꾼 값이 공개 사이트(3100)에 **그대로, 제때** 드러나는가. 저장·되돌리기·검증·캐시 반영 (항목 목록은 3절) |
| **P0** | B. 역할·권한 | 운영자 역할별로 메뉴 노출·화면 진입·저장 버튼·API 거절(403)이 권한 표와 맞는가. 권한 상승이 막히는가 (4절) |
| P1 | C. 관리자 전체 화면 | 나머지 관리 화면(회원·신고·제재·포인트·커머스·광고·통계·시스템)의 목록·검색·상세·처리 기본 흐름 (5절) |
| P1 | D. 성능 | 화면 첫 로딩·API 응답·요청 수·저장 뒤 공개 반영 시간 (6절) |
| P2 | E. 계정·보안 | 운영자 로그인·잠금·세션·초대·비밀번호 재설정·감사 기록 (4-4절) |

범위 밖: 결제 실제 승인(PG), 외부 연동 실제 발송(카카오·슬랙), 법무 문구 검토, 모바일 앱.

## 1. 환경
| 항목 | 값 |
|---|---|
| 관리자 화면 | http://localhost:3200 (run-develop dev) — 시험 대상 코드와 같은 커밋인지 시작 전에 확인 |
| 공개 화면 | http://localhost:3100 |
| 서버 | api 8910 · admin 8920 (jar) |
| DB | `irobit-local-postgres` (5420, DB·계정 irobit) |
| 메일 | Mailpit http://localhost:8035 (운영자 초대·비밀번호 설정 링크 확인) |
| 브라우저 | 사용자 Chrome + Claude in Chrome 확장 (내장 브라우저는 쓰지 않음) |

**시작 전 준비**
1. 서버 4개가 같은 코드인지 확인(`git log -1` — run-develop·jar 만든 커밋). 지금 api·admin 은 포인트 게임 브랜치 jar(develop ba10dd88 과 같은 내용, 미푸시)다.
2. **로컬 DB 백업**: `pg_dump -Fc` 를 컨테이너 `/tmp/irobit-before-admin-qa.dump` 로. QA 가 설정값을 많이 바꾸므로 끝나면 이 백업으로 되돌릴지 사용자에게 묻는다.
3. 시험 운영자·역할 만들기(4-1절). 비밀번호는 시험용으로 만들고 `docs/qa/admin-qa-accounts.local.md`(git 제외)에만 적는다.
4. 시험 회원(공개 사이트 확인용): 비로그인 / 새싹 / 정식 이상 / 성인 인증 / 홍보 전용(사업자) / 게시판 매니저·스텝 / 운영자 회원 계정. 데모 데이터 회원 중 골라 쓰고, 없으면 만든다.

## 2. 진행 방식
- 화면 하나씩: **(1) 현재 값 기록 → (2) 값 바꿔 저장 → (3) 공개 사이트에서 확인(새로고침·다른 회원으로도) → (4) 원래 값으로 되돌림**. 되돌림까지 해야 그 항목 끝.
- 각 단계에서 Chrome 콘솔 오류·네트워크 실패(4xx/5xx)를 같이 본다.
- 결과는 `docs/qa/admin-qa-log.md` 에 줄 단위로: `화면 | 항목 | 역할 | 결과(통과/실패/보류) | 증거(요청·응답·스크린샷) | 조치`.
- **버그를 찾으면**: 원인 확인 → 작업 브랜치(`claude/admin-qa-fixes`, 별도 worktree)에서 고침 → 바꾼 범위의 최소 컴파일·타입 검사 → 그 화면 다시 시험 → 로그에 커밋 번호. 서버 정책을 바꿔야 하는 일(권한 정의·업무 규칙)은 고치지 않고 질문으로 모은다. 푸시·develop 병합은 사용자 확인 뒤.
- 브라우저 확인(confirm) 창은 확장을 멈추게 하므로, 삭제처럼 확인 창이 뜨는 동작은 앞에서 미리 알리고 한다.

## 3. 공개 사이트 설정 항목 (P0)
> 화면별 항목·저장 API·공개 반영 위치·캐시는 아래 표. 모든 항목에 공통 시나리오 A-1~A-6 를 적용한다.

**공통 시나리오**
| # | 조건 | 수행 | 기대 결과 |
|---|---|---|---|
| A-1 | 최고 관리자 | 값 바꿔 저장 | 성공 알림, 새로고침해도 값 유지, 감사 로그에 남음 |
| A-2 | 저장 직후 | 공개 사이트 새로고침 | 바뀐 값이 보인다. 캐시가 있으면 저장 때 비워지거나 안내된 시간 안에 반영 |
| A-3 | 잘못된 값(빈 값·길이 초과·형식 오류·범위 밖) | 저장 | 칸 아래 오류 문구, 서버도 400 으로 막음(화면 검사만 있고 서버가 통과시키면 버그) |
| A-4 | 저장 안 하고 이동 | 다른 메뉴 클릭 | 바뀐 값이 있으면 이동 확인(있는 화면만), 저장 안 된 값이 남지 않음 |
| A-5 | 원래 값으로 되돌림 | 저장 | 공개 사이트도 원래대로 |
| A-6 | 두 탭에서 같은 설정 | 앞 탭 저장 후 뒤 탭 저장 | 다른 칸이 지워지지 않음(낡은 화면이 모르는 칸을 덮어쓰는지) |

**캐시 기준**: 저장 → 감사 기록 → `CacheAutoRefresh` 가 캐시 세대 번호를 올림 → api 서버 `CacheSync` 가 3초마다 확인. 비우는 캐시가 연결된 항목은 **약 3초 안**, 연결 안 된 항목은 그 캐시 TTL 안에 반영돼야 한다. 시작 전에 `/settings/caches` 에서 캐시 상태(켜짐·TTL)를 기록한다.

## 4. 역할·권한 (P0)
### 4-1. 시험 운영자와 역할
권한 원천은 서버 `Permission`(enum)과 `AdminScreenRegistry`(화면별 읽기 권한)다. 로컬 DB 에는 지금 최고 관리자와 데모 운영자(데모 데이터 넣기 역할)만 있어서 아래 역할·계정을 새로 만든다. 계정은 **운영자 직접 추가 → Mailpit 의 비밀번호 설정 링크**로 만든다(그 자체가 E 시나리오).

| 계정 | 역할(유형) | 권한 | 확인할 것 |
|---|---|---|---|
| QA-ROOT | 최고 관리자(기존 루트) | 전부 | 기준선 |
| QA-LAYOUT | 사이트 화면 구성 | `layout.read` `layout.settings` | 메뉴·테마·가젯 페이지 저장 가능, 사이트 일반 설정은 못 바꿈 |
| QA-LAYOUT-RO | 사이트 화면 구성(읽기) | `layout.read` | 화면은 보이지만 저장 버튼 숨김/비활성, API 직접 호출도 403 |
| QA-SITE | 사이트·연동 | `site.read` `site.manage` | 일반 설정·팝업·공지 띠 등 저장, 키·비밀 칸은 못 봄/못 바꿈 |
| QA-SITE-SECRET | 사이트·연동 | + `site.secret` | 소셜 로그인·포트원·메일 서버 키 보기·바꾸기 |
| QA-BOARD | 게시판 구성 | `board.read` `board.manage` `board.settings` | 게시판·기본값 저장, 게시판 삭제는 못 함 |
| QA-BOARD-DEL | 게시판 구성 | + `board.delete` `board.staff.*` | 삭제·매니저/스텝 지정·한도 |
| QA-CONTENT | 공지·주요글 | `notice.*` `highlight.*` `popular.*` | 공지·하이라이트·인기글 설정 |
| QA-POINT | 등급·포인트 | `grade.*` `point.read` `point.settings` `pointshop.*` `emoticon.read/settings` `reward-event.*` | 등급·포인트 정책·상점·로보티콘 설정 |
| QA-BIZ | 핫딜·광고·소모임·커머스 설정 | `hotdeal.*` `ad.read` `ad.settings` `group.*` `commerce.settings` | 각 영역 설정 저장 |
| QA-SAFETY | 신고·제재 | `report.*` `sanction.read/manage` | 설정 화면 메뉴가 안 보이고 직접 주소로 들어가도 막힘 |
| QA-READALL | 종합(읽기만) | 모든 `*.read` | 모든 화면 진입, **저장 버튼이 하나도 안 통해야 함** |
| QA-NONE | 역할 없음 | 없음 | 대시보드만, 나머지 메뉴·주소·API 전부 막힘 |
| QA-OPMGR | 운영자·역할 관리 위임 | `operator.*` `role.read` `role.manage` `role.grant` + `layout.read` | 자기 권한 밖 권한을 역할에 넣거나 남에게 줄 수 없음(권한 상승 방지), 종합 관리 유형은 못 만듦 |

### 4-2. 역할마다 공통 시나리오
| # | 수행 | 기대 결과 |
|---|---|---|
| B-1 | 로그인 후 왼쪽 메뉴 | 가진 읽기 권한 화면만 보임(`AdminScreenRegistry` 와 일치) |
| B-2 | 권한 없는 화면 주소를 직접 입력 | 권한 없음 화면/대시보드로 보냄, 화면 안 데이터 요청은 403 |
| B-3 | 읽기만 있는 화면 | 저장·삭제·추가 버튼 숨김 또는 비활성, 칸이 읽기 전용 |
| B-4 | 읽기만 있는 상태에서 저장 API 를 콘솔로 직접 호출 | 403 + 감사 로그 「권한 거부」 |
| B-5 | 다른 탭에서 최고 관리자가 이 운영자의 역할을 빼면 | 다음 요청부터 바로 막힘(세션이 옛 권한을 들고 있지 않음) |
| B-6 | 화면 안의 하위 탭·패널(예: 게시판 상세의 매니저 탭, 사이트 설정의 키 칸) | 세부 권한(`board.staff.manage`, `site.secret`)에 맞게 숨김/막힘 |

### 4-3. 권한 상승·경계
- 역할 관리 위임 운영자(QA-OPMGR)가: 자기에게 없는 권한을 역할에 넣기 / 자기보다 큰 역할을 남에게 주기 / 자기 역할 고치기 / 종합 관리 유형 만들기 / 최고 관리자 잠그기 → 모두 거절.
- 마지막 최고 관리자 잠금·삭제 불가, 내장 역할 삭제 불가.
- 관리자 메뉴 편집(`admin-menu.manage`) 없는 운영자는 관리자 메뉴 순서를 못 바꿈.

### 4-4. 계정·보안 (P2)
운영자 직접 추가 → 초대 메일 → 비밀번호 설정 / 초대 만료·취소 / 비밀번호 5회 틀림 잠금 → 해제 / 계정 기간 밖 로그인 막힘 / 사용 중지 계정 로그인 막힘 / 비밀번호 재설정 / 비활동 세션 만료 / 로그인 보안 화면(최고 관리자 전용) / 감사 로그에 로그인 성공·실패·권한 거부·역할 변경이 남는지.

### 4-5. 공개 사이트 회원 쪽 확인
설정이 회원 종류에 따라 다르게 보이는 항목(게시판 읽기·쓰기 등급, 19금·성인 게시판, 익명 게시판, 홍보 전용 계정 허용 게시판, 매니저·스텝 처리 한도, 운영자 회원 계정 표시)은 비로그인·새싹·정식 이상·성인 인증·홍보 전용·매니저/스텝·운영자 회원 계정으로 각각 공개 사이트에서 확인한다.

## 6. 성능 (P1)
| 측정 | 방법 | 기준(로컬, 가정) |
|---|---|---|
| 화면 첫 로딩 | `performance.getEntriesByType('navigation')`, 화면 이동은 클릭~데이터 표시 | 1.5초 이하 |
| API 응답 | `performance.getEntriesByType('resource')` 의 `/api/` 요청 시간·크기 | 대부분 300ms 이하, 1초 넘으면 원인 확인 |
| 요청 수 | 한 화면을 열 때 `/api/` 요청 개수, 같은 요청 반복 여부 | 같은 요청 2번 이상이면 확인 |
| 응답 크기 | 목록 API 크기 | 200KB 넘으면 페이지 나눔·필드 확인 |
| 공개 반영 시간 | 저장 시각 → 공개 사이트에 보인 시각 | 캐시 비우는 항목은 즉시, 아니면 캐시 TTL 안 |
| 느린 쿼리 | 느린 API 는 서버 로그·`EXPLAIN ANALYZE` 로 원인 | 인덱스 없는 전체 훑기·N+1 이면 기록 후 수정 |
