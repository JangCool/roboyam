# 역할 · 운영자 · 등급 계약 (**화면 확정 2026-10-21** — 백엔드 구현 단계)

**의도**: 운영자(관리자 앱 계정)와 그 역할·권한, 회원 역할(등급·회원 유형·게시판 단위·사용자 정의), 등급 설정을 관리자 앱에서 다룬다. 화면은 확정됐고(`apps/admin-web` 목업이 기준), 서버는 아직 `server/admin` 에 진입점만 있다(`V1~V6`).

## 백엔드 구현 순서와 가정 (2026-10-21)
단계는 순서대로 한다(앞 단계가 뒤 단계의 기반이다). 한 단계가 끝나고 사용자가 확인한 뒤 다음으로 간다.
1. **운영자 기반**(이번 단계): 권한 카탈로그(코드 enum `영역.행위`, 시작 때 DB 와 맞춤) · `operators`/`roles`/`role_permissions`/`operator_roles` 표 · 관리자 서버 로그인·세션·`me` · 권한 검사(`@RequirePermission` + 인터셉터, **선언 없는 API 거절** fail-closed) · 역할 API · 운영자 API(+초대·반려) · 설치 마법사 루트 계정을 `operators` 의 최고 관리자로 · 감사 기록 쓰기(표·서비스).
2. 등급 설정 + 회원 조회(읽기): 지금 있는 표(`users`·`profiles`)로 가능한 범위만. 포인트·동의 이력·공동구매 등 아직 기능이 없는 칸은 목업으로 남긴다.
3. 사이트 일반 설정(`site-settings-contract.md`): 이미지 업로드·변환·저장소.
4. 내 정보(`/api/admin/profile`)와 감사 로그 조회(`/api/admin/audit-logs`) — 읽기/본인 것 위주.
5. 운영자 비밀번호 흐름 — 초대 수락·비밀번호 재설정(승인번호)·내 비밀번호 변경(`/api/admin/auth/*`, `/api/admin/profile/password`).
6. 운영자 계정 보강(서버만) — 직접 추가↔대기 초대 충돌 방지, 운영자 이름 유일(대소문자 무시, `V30`), 로그인 이력 접속 환경(User-Agent 요약).
- **1단계 구현 결과(2026-10-21)**: Flyway shared `V7`(operators·permissions·roles·role_permissions·operator_roles·user_roles·operator_invitations·audit_logs)·`V8`(기존 ADMIN·STAFF 회원을 `operators` 로 이전, `users.role` 을 `USER` 만 허용), admin 스트림 `V1`(`admin_session`). 권한 78개(운영자)+19개(회원) enum 이 원천이고 기동 때 DB 와 맞춘다. 관리자 API 17개는 모두 `@RequirePermission`/`@AdminAuthenticated`/`@AdminPublic` 선언이 있어야 기동한다(fail-closed). 오류 코드는 프론트 목업 기준에 더해 `PERMISSION_DENIED`·`ROLE_TYPE_DERIVED`(등급 파생에 만들기)·`ROLE_GENERAL_SUPER_ONLY`·`ROLE_IN_USE` 등. 로그인 `role` 은 호환용이며 판정은 `isSuper`·`permissions` 로 한다. 초대 수락 경로는 `{ADMIN_URL}/invitation?token=` 로 가정(수락 API·화면 미구현), 운영자 생성은 임시 비밀번호를 메일로 안내(재설정 기능 없음). 서버 시드에는 영역별 관리자 같은 운영자 역할이 없고 내장 역할은 회원 4개뿐이다. 반려한 신청은 행을 지우고 감사 기록에만 남긴다.
- **2단계 구현 결과(2026-10-21)**: Flyway shared `V9__grades`(`grades`·`grade_settings` 신설, `profiles.grade` → `grade_key` FK 이전 후 칸·CHECK 삭제, `grade_manual`·`bio`, `ix_users_created`). `grade_rules` 표는 아무도 읽지 않지만 삭제하지 않았다(→ 배치 인프라 단계의 V11 에서 삭제). **배포 주의: `profiles.grade` 를 지우므로 api·admin 을 같은 버전으로 함께 올린다.** API: `GET/PUT /api/admin/grades`, `POST …/grades/preview`, `GET /api/admin/members`·`…/{id}`·`…/role-options`(권한 `grade.read`/`grade.manage`/`member.read`, 이메일은 `member.pii` 없으면 마스킹, 상세 열람은 감사 `MEMBER_VIEW`). 오류: `GRADE_LIMIT`·`GRADE_FIRST_PROTECTED`·`GRADE_NAME_DUPLICATED`·`GRADE_RULES_NOT_MONOTONIC`(409, `fields` 없음)·`MEMBER_NOT_FOUND`·`MEMBER_PERIOD_REVERSED`·`MEMBER_POINT_RANGE_REVERSED`. 등급 저장 때 `ROLE_GRADE_<키>` 파생 역할이 만들어지고(기본 권한 = 바로 아래 등급 복사) 삭제·이름 변경도 따라간다. 승급 판정(`GradePromotionService`)은 가입 일수·활동 수 AND 조건, ACTIVE 회원만, 올리기만 한다. 활동 수는 글·댓글 표가 없어 0 으로 본다(**활동 조건이 있는 등급은 그 표가 생기기 전까지 도달 불가**). 일수 승급 배치는 배치 인프라 단계에서 연결됐고(아래 — 지금은 DB 배치 `grade-promotion`, 예전 `promoteByElapsedTime` 은 없앴다), 글/댓글 작성 시 즉시 판정(`promoteOnEvent`) 호출 지점은 아직 없다. 회원 상세에서 서버가 비워 주는 칸(포인트·활동·제재·신고·동의 상세·알림 설정·공동구매·연락처·프로필·휴면 등)은 null/빈 배열 — 프론트 `MemberDetail` 타입을 nullable 로 바꾸고 빈 구획을 EmptyState 로 처리해야 한다. 공개 `gradeLabel` 은 이제 운영자가 입력한 한국어 이름이다(영어 이름 `labelEn` 은 후속).
- **배치 인프라 결과(2026-10-21)** — 화면 계약은 `docs/features/batch-contract.md`.
  - **구조**: 배치 **정의의 원천은 코드**(`admin` `BatchCatalog` enum — 키·분류·기본 cron·기본 사용 여부, 이름·설명은 메시지 번들 `batch.job.<키>.name/desc`)이고 서버가 뜰 때 DB `batch_jobs` 와 맞춘다(없는 배치만 기본값으로 넣고, 운영자가 바꾼 값은 덮어쓰지 않으며, 카탈로그에서 사라진 행은 지운다). **새 배치 = `BatchJob` 구현(빈) 1개 + 카탈로그 1줄 + 번들 문구**(짝이 안 맞으면 기동 실패). 일은 `BatchResult(처리 건수, 요약 문구 키+인자)` 를 돌려주고 예외로 실패를 알린다. 실행 주체는 **관리자 서버(`server/admin`)** 다 — 배치를 켜고·끄고·바꾸고·돌리는 곳이 관리자 앱이고, 공개 서버(`api`)는 스케줄러를 갖지 않는다. 엔티티·QueryDSL 저장소는 `shared`(Q 클래스 생성 위치), 나머지는 `admin` `com.community.batch`.
  - **테이블**(Flyway shared `V10__batches`): `batch_jobs`(`job_key` PK, `enabled`, `cron`, 마지막 실행 요약 `last_*`, `updated_by`) · `batch_runs`(실행 로그: `id`, `job_key`, `status` RUNNING/OK/FAIL/SKIP, `trigger_type` SCHEDULED/MANUAL, `scheduled_at`, `started_at`, `finished_at`, `affected_count`, `message_key`+`message_args`(요약, 요청 언어로 풀림), `error_message`, `operator_id`, `node_id`). 유일 색인 2개: `(job_key, scheduled_at)`(예약 시각마다 한 줄 — 서버가 여러 대여도 한 번만) · `(job_key) WHERE RUNNING`(동시에 하나만 실행 중). `V11__drop_grade_rules` — `grade_rules` 삭제(코드·이후 마이그레이션 어디서도 읽지 않음을 확인, 데이터는 V9 에서 `grades` 로 이전됨).
  - **스케줄러·cron**: Spring 내장 `ThreadPoolTaskScheduler` + `CronExpression`(의존성 추가 없음). 6칸 식(초 분 시 일 월 요일), 시간대 `Asia/Seoul`(`roboyam.batch.zone`). 서버가 켜진 배치마다 다음 실행 시각(slot)을 직접 계산해 그 시각에 한 번 예약하고 끝나면 다시 계산한다 — 서버가 여러 대여도 slot 이 같다. 사용 여부·cron 은 DB 가 원천이라 **재기동 없이** 바뀐다: 변경한 서버는 커밋 직후(`@TransactionalEventListener`), 다른 서버는 `roboyam.batch.refresh-seconds`(30초) 주기 폴링으로 따라온다. 서버가 내려가 있던 동안의 시각은 되살리지 않는다. 설정 키(`admin application.yml` `roboyam.batch.*`): `scheduler-enabled`(true) · `zone` · `refresh-seconds` · `min-interval-seconds`(60) · `log-retention-days`(90) · `pool-size`(4).
  - **중복 실행 방지(락)**: 배치마다 PostgreSQL 어드바이저리 잠금(세션 잠금, `pg_try_advisory_lock(7340002, hashtext(키))`, 배치가 도는 동안 연결 하나를 쥠 — 서버가 죽으면 DB 가 연결과 함께 풀어 준다)과 위 유일 색인의 이중 방어. 잠금을 못 잡은 쪽은 예약이면 조용히 건너뛰고 수동이면 409 `BATCH_RUNNING`. **비정상 종료로 남은 「실행 중」 줄**: 잠금을 쥔 쪽은 지금 그 배치를 돌리는 서버가 없다는 뜻이라, 기동 때·폴링(30초)마다·다음 실행 직전에 남은 RUNNING 줄을 FAIL(`batch.error.interrupted`)로 닫는다 — 다른 서버가 정말로 돌리는 중이면 잠금을 못 잡아 건드리지 않는다.
  - **실행 결과**: 일이 정상 종료하면 처리 건수 0 → `SKIP`(건너뜀, 「할 일 없음」), 1 이상 → `OK`, 예외 → `FAIL`(사유는 가장 깊은 원인의 예외 이름 + 첫 줄, 이메일·password/token 값·PostgreSQL `Key (칸)=(값)` 의 값을 가려 500자까지 — 전체 스택트레이스는 서버 로그에만). 꺼진 배치의 예약은 아무것도 남기지 않고, **수동 실행은 꺼져 있어도 돈다**.
  - **API**(`/api/admin`, 권한은 카탈로그의 `batch.*` — 새 권한 코드 추가 없음): `GET /batch-jobs`(`batch.read`) · `PUT /batch-jobs/{jobName}` `{enabled}`(`batch.manage`) · `PUT /batch-jobs/{jobName}/schedule` `{schedule}`(`batch.manage`) · `POST /batch-jobs/{jobName}/run`(`batch.run` 민감 조치, **끝날 때까지 기다림**, 실행 중이면 409) → 모두 **바뀐 목록 전체** `BatchJobView[]`; `GET /batch-logs?jobName&status&trigger&from&to&page&size`(`batch.read`, 시작 시각 최근순, `size` 1~100 기본 20) · `GET /batch-logs/{logId}`. 오류: 404 `BATCH_NOT_FOUND`·`BATCH_LOG_NOT_FOUND`, 409 `BATCH_RUNNING`, 400 `VALIDATION`(`fields.schedule`/`jobName`/`status`/`trigger`/`from`/`to`/`page`/`size`). 감사: `BATCH_TOGGLE`·`BATCH_SCHEDULE_CHANGE`(변경이 있을 때만, 전후 값)·`BATCH_RUN`(실행 결과 포함, 일이 실패해도 요청은 200).
  - **cron 안전장치(가정)**: 6칸이 아니거나 해석 불가·앞으로 실행 시각 없음(예: 2월 30일)·**앞으로 64번의 실행에서 인접 실행 간격이 60초 미만**(초 칸에 여러 값/`*`)이면 400 `fields.schedule`.
  - **등록된 Java 배치**: `file-orphan-cleanup`(3단계) 하나뿐이다. 정리 배치와 **`grade-promotion` 「등급 일수 승급」도 DB 배치로 옮겼다**(아래). `batch-log-cleanup`·`grade-promotion` 은 예전에 Java 배치였다 — 같은 키를 이어 써서 쌓인 로그·화면 이름이 그대로고, 옛 `batch_jobs` 행은 기동 때 `BatchCatalogSynchronizer` 가 지운다(카탈로그의 Java 배치에 없는 행 삭제).
  - **`grade-promotion` = DB 배치(2026-10-21 옮김, 사용자 지시)**: 분류 MEMBER, 프로시저 `batch_grade_promotion`(반복 마이그레이션 `R__batch_15_grade_promotion.sql`), 기본 매일 04:30 KST(정책 문서 미확정 11 의 **가정** — 기본 cron 은 카탈로그가 아니라 SQL 의 `batch_define` 이 가진다), 처리 건수 = 승급 인원(0 이면 SKIP), 설정값 `chunk_size`(5000)·`max_per_run`(1000000, 상한에 닿으면 `batch.result.gradePromotion.capped` 문구로 끝내고 나머지는 다음 실행). 덩어리마다 `grade_settings` 행을 `FOR UPDATE`(30초 lock_timeout)로 잠가 등급 저장과 겹치지 않게 하고 **저장이 끝난 등급 목록**으로 판정한다(Java 가 하던 것과 같은 의도). **이중 구현 주의**: 같은 판정이 Java(`GradePromotionService.promoteAll`·`promoteOnEvent`, `GradeRepositoryQDSL#promotable` — 등급 저장 직후 소급 승급·글/댓글 작성 때 즉시 승급용)와 SQL 두 곳에 있다. 어느 쪽을 고치면 다른 쪽도 고치고(코드·SQL 주석에 서로를 가리킨다) 같은 데이터에서 같은 결과를 내는지 확인한다. 등급 설정 저장 직후의 소급 승급은 Java 그대로이고(활동 조건·새 등급·옵션 변경은 즉시, 일수 조건을 낮춘 몫은 저장 전·후 일수 중 큰 값으로 판정) 낮춘 몫은 이 DB 배치가 올린다. **업무 배치라 pg_cron 이 없으면 승급이 돌지 않는다** — 목록에 「사용 불가」+이유가 보이고 기동 때 WARN 로그가 남는다(`BatchCatalog#isBusinessCritical`). Java 폴백(pg_cron 이 없을 때만 Java 가 대신 도는 방식)은 만들지 않았다.
  - **DB 배치(저장 프로시저 + pg_cron, 2026-10-21)** — 상세는 `batch-contract.md` 「DB 배치」, 규칙은 `.claude/guides/backend/db-batch.md`. Java 배치와 한 화면·한 API·한 로그 표(`batch_runs.source = POSTGRESQL`). 실행 주체는 DB(pg_cron)라 서버 대수와 무관하게 한 번, 관리자 서버가 내려가 있어도 돈다. 사용 여부·cron 은 `cron.job` 이 원천(`cron.alter_job`), 정의는 카탈로그(이름·설명·분류) + `batch_db_jobs`(프로시저·기본 cron) + `batch_params`(보관 일수·덩어리·상한). Flyway shared `V20__db_batches`(`batch_runs.source`·`batch_db_jobs`·`batch_params`·색인) + 반복 마이그레이션 `R__batch_00_helpers`(공통 함수) · `R__batch_10~15_*`(프로시저+등록, 운영자가 바꾼 cron·사용 여부·설정값을 덮어쓰지 않는다). 이미지: 공식 `postgres:18` + `postgresql-18-cron`(`docker/postgres/`, 설치기 `templates/postgres/`), 서버 설정 `shared_preload_libraries=pg_cron`·`cron.database_name`·`cron.use_background_workers=on`·`cron.timezone=Asia/Seoul`. **pg_cron 이 없어도 서버·Java 배치는 정상** — DB 배치만 `available=false` + 이유. 정리 배치(쌓이는 표 조사 결과, 보관 값은 모두 `batch_params` 로 바꾼다):

  - **초대 수락**: 토큰은 본문으로 받고(주소·로그에 남지 않는다) SHA-256 해시로 `operator_invitations.token_hash` 와 견준다. 한 트랜잭션에서 초대 행을 `FOR UPDATE` 로 잠가 동시 수락을 막고(두 번째는 `INVITATION_USED`) 운영자를 만든다 — 승인됨·사용 중·잠금 없음·기간 제한 없음, 이름 = 닉네임(내 정보와 같은 `UserPolicy` + 같은 어드바이저리 잠금 `7340003` 으로 중복 확인), 비밀번호 = 공개 사이트 규칙(8~64자·영문+숫자·UTF-8 72바이트 이하). 초대의 역할을 부여한다(역할을 공유 잠금으로 읽어 부여 중 삭제를 막는다. 역할이 지워지면 `operator_invitation_roles` 가 연쇄 삭제되므로 건너뛸 일은 사실상 없고, 경합으로 빠진 역할이 있으면 감사에 `rolesSkipped`). 감사 `INVITATION_ACCEPT`(행위자·대상 = 새 운영자, `invitationId`·`roles`; 비밀번호·토큰·이메일 없음). **취소한 초대는 행을 지우므로 `INVITATION_NOT_FOUND` 로 보인다**(프론트의 `INVITATION_CANCELED` 410 은 서버에서 나오지 않는다 — 두 상태 다 지원하면 된다).
  - **비밀번호 재설정(하모니카3 방식)**: ① `code` — 승인번호(`SecureRandom` 숫자 6자리, 앞자리 0 허용)를 만들어 **salt + SHA-256 해시로만 저장**(이메일 해시 키마다 한 행 — 새로 받으면 같은 행을 새 번호로 바꿔 이전 번호 무효·틀린 횟수 0) · 유효 10분 · 메일은 커밋 뒤 **별도 스레드풀(2개, 대기열 100)** 이 보낸다(`PasswordResetMailSender`; 메일 서버 미설정·실패는 경고 로그만 — 번호·주소·예외 문구는 로그에 안 남긴다). ② 확인 — 입력 형식 검사(약한 비밀번호가 시도 횟수를 쓰지 않게 먼저) → 행 잠금으로 번호 확인(없음 → 이미 씀 → 만료 → 소진 → 틀림 순) → 계정 상태 확인(403) → 비밀번호 해시 교체·번호 소진·**그 운영자의 모든 세션 종료**(`admin_spring_session.principal_name = operator:<ID>`, `AdminSessionTerminator`)·`login_attempts`(`admin:` 키) 초기화·마지막 로그인 시각 갱신 → 감사 `PASSWORD_RESET`(`sessionsEnded`)·`LOGIN_SUCCESS`(`via=PASSWORD_RESET`) → 컨트롤러가 세션 고정 방지로 세션을 새로 만들어 로그인시킨다. 번호를 5번 틀리면 소진(`CERT_CODE_EXHAUSTED`)돼 새로 받아야 하고, 틀린 횟수는 오류 응답에서도 남는다(`noRollbackFor`). 소진은 감사 `PASSWORD_RESET` 실패(`CODE_EXHAUSTED`), 상태가 막힌 계정이 맞는 번호를 내면 감사 `PASSWORD_RESET` 거부(`NOT_ALLOWED`)로 남는다.
  - **방어 설계**: ⓐ **계정 열거** — 승인번호 요청은 없는 이메일·잠금/미승인/만료/사용 중지/기간 밖 계정에도 **같은 응답·같은 작업량**(한도 확인·기록, 번호 생성·해시, 승인번호 행 쓰기, 감사 한 줄)을 하고 메일만 대상에게 간다. 대상이 아니면 **가짜 행**(`operator_id NULL`, 아무에게도 전달되지 않는 번호)을 만들어, 이후 확인 응답(없음/틀림 횟수/소진/만료)이 실제 계정과 한 글자도 다르지 않다(없는 이메일이 `NOT_FOUND` 이고 있는 이메일이 `INVALID` 로 갈리면 요청 뒤 한 번의 확인으로 존재를 알아내기 때문). 감사 기록도 대상이 아니면 익명 실패 한 줄(`NO_ACCOUNT`/`NOT_ALLOWED` + 이메일 해시 조각)을 남긴다. ⓑ **타이밍** — 위 같은 작업량 + 메일을 요청 스레드가 아닌 풀에서 보냄. 일회용 DB 에서 실제 계정 56회·없는 계정 56회를 번갈아 잰 평균 15.41 vs 15.44 ms(중앙값 13.9 vs 13.4)로 차이가 없었다. 확인 쪽도 모든 경로에서 계정 조회를 똑같이 하고, 느린 비밀번호 해시는 번호가 맞은 뒤에만 한다. ⓒ **무차별 대입** — 번호 6자리는 해시로 못 지킨다(100만 가지)는 전제에서, 번호당 5번 + 유효 10분 + 요청 한도(아래)로 시간당 추측 수를 25회로 묶는다(확률 약 2.5×10⁻⁵). 같은 번호의 동시 시도는 행 잠금으로 줄 세워 12개 동시 요청에도 틀린 횟수가 5를 넘지 않음을 확인했다. 번호는 맞아도 한 번 쓰면 못 쓴다. ⓓ 토큰·번호·비밀번호는 로그·오류·감사·`toString` 에 없다(요청 DTO·이벤트의 `toString` 은 값을 감춘다).
  - **요청 한도(가정, `roboyam.admin-auth.password-reset.*` 설정값)**: 같은 이메일(해시 키) **쿨다운 60초 + 창 60분 안에 5회**, 같은 IP **창 안에 20회**(IP 쿨다운은 없다 — 한 사무실의 서로 다른 운영자가 막히지 않게). 받아들인 요청만 `operator_cert_requests`(키 해시·시각) 한 줄씩(이메일 키·IP 키 각각) 쌓고, 가입 여부와 무관하게 센다. 초과는 429 + `retryAfterSeconds`(쿨다운/창 중 가장 긴 대기). 확인·기록 경합은 두 키에 거는 트랜잭션 어드바이저리 잠금(`7340004`, 키 정렬 순서라 교착 없음)으로 줄 세운다. **알려진 한계**: 남의 이메일로 시간당 5번 요청하면 그 사람의 재설정을 한 시간 막을 수 있다(존재를 노출하지 않는 대가) — 필요하면 한도·창을 조정한다.
  - **저장·정리**: `login_attempts` 는 「연속 실패 → 잠금」 한 행이라 시각별 요청 창·쿨다운을 담지 못해 재사용하지 않고 새 표를 만들었다(승인번호는 이메일 키마다 한 행으로 새로 받으면 덮어쓴다). 쌓이는 건 DB 배치 `auth-token-cleanup`(프로시저 `batch_auth_token_cleanup`)이 지운다 — **같은 프로시저에 두 표를 더했다**: 승인번호는 만료 후 `retention_days`(7)일, 요청 기록은 `request_retention_hours`(24, 최소 2 — 한도 창 1시간보다 길게)시간 지난 행. 처리 건수는 세 표(`auth_tokens`+두 표)의 합이고 덩어리(`chunk_size`)·상한(`max_per_run`)은 세 표가 나눠 쓴다. `request_retention_hours` 는 `batch_param_seed` 로 처음에만 넣어 운영자가 바꾼 값·cron 은 덮어쓰지 않는다(`R__` 를 다시 적용해도 바뀐 cron 이 `KEPT`). 메시지 `batch.job.auth-token-cleanup.*`·`batch.result.authTokenCleanup*` 문구를 「인증 토큰·승인번호·요청 기록」으로 고쳤다. 감사 보관 배치와 무관.
  - **비밀번호 변경**: 현재 비밀번호를 `bcrypt` 로 대조(틀리면 **400** `INVALID_CURRENT_PASSWORD` — 401 이면 공통 클라이언트가 세션 만료로 보고 로그인으로 보낸다), 검사 순서는 입력 형식 → 현재 비밀번호 → 새 비밀번호가 현재와 같은지. 성공하면 **지금 세션은 유지하고 다른 세션은 모두 종료**(요청의 세션 ID 만 제외), 감사 `PASSWORD_CHANGE`(`sessionsEnded`). 틀린 시도는 감사 `PASSWORD_CHANGE` 실패(`CURRENT_PASSWORD_MISMATCH`)로 따로 남는다. **현재 비밀번호의 연속 오류는 로그인 잠금(`login_attempts`)에 합산하지 않는다(가정)** — 이미 로그인한 세션이 요구되고 요청마다 bcrypt 비용이 든다. 세션 탈취 상태의 무차별 대입 제한은 후속.
  - **새 오류 코드/키**: `INVITATION_EXPIRED`·`INVITATION_USED`·`TOO_MANY_REQUESTS`·`CERT_CODE_INVALID|EXPIRED|USED|EXHAUSTED|NOT_FOUND`·`PASSWORD_RESET_NOT_ALLOWED`·`INVALID_CURRENT_PASSWORD`(`INVITATION_NOT_FOUND` 는 공개 링크용 문구 키 `error.INVITATION_LINK_NOT_FOUND` 를 쓴다). 칸 문구 `operator.certCode.format`·`profile.password.current.required`·`profile.password.new.same`, 메일 `mail.operatorReset.*`, 감사 작업 `INVITATION_ACCEPT`·`PASSWORD_RESET_REQUEST`·`PASSWORD_RESET`·`PASSWORD_CHANGE`(+사유 `CODE_EXHAUSTED`·`CURRENT_PASSWORD_MISMATCH`) — 모두 ko/en 두 번들.
  - **프론트 `// MOCK:` → `// REAL:` 때 어긋나는 점**
    1. **재설정 성공이 204 가 아니라 200 + 로그인된 `me`** 다(자동 로그인 확정). `resetPassword` 의 반환 타입을 `AdminMeResponse`(= `useAdminAuthApi` 의 로그인 응답)로 바꾸고, 화면은 `/login` 으로 보내지 않고 인증 상태를 갱신(`useAdminAuth().refresh()` 또는 응답으로 세팅)한 뒤 `/` 로 보낸다(`forgot-password.vue` 의 `// REAL:` 줄). 모든 기존 세션이 끝났으므로 다른 탭은 다음 요청에서 401.
    2. 재설정 오류: `fields.email`(형식)도 올 수 있다(화면은 지금 `certCode`·`newPassword` 만 칸에 붙인다). 새 코드 **403 `PASSWORD_RESET_NOT_ALLOWED`**(승인번호는 맞는데 그 사이 계정이 잠금 등) — `CERT_CODE_` 묶음이 아니므로 별도 처리(서버 문구를 화면 위쪽에). 승인번호 형식이 틀리면 `CERT_CODE_INVALID` 가 아니라 `VALIDATION` `fields.certCode`(숫자 6자리 아님).
    3. 승인번호 요청: `fields.email` 400, 429 `TOO_MANY_REQUESTS`(+`retryAfterSeconds`). 가입 여부와 무관하게 늘 200 이므로 「메일을 보냈어요」 문구는 「가입된 이메일이면 보냈어요」 뉘앙스를 유지한다. 메일 서버가 없어도 200 이다.
    4. 초대: `INVITATION_CANCELED`(410)는 오지 않는다 — 취소는 `INVITATION_NOT_FOUND`(404). 수락 오류에 **409 `OPERATOR_EMAIL_DUPLICATED`**(그 사이 같은 이메일 운영자가 생김)가 더해졌다(칸이 아니라 위쪽 안내). `INVITATION_USED` 는 만료와 무관하게 수락했으면 늘 409.
    5. `INVALID_CURRENT_PASSWORD` 400 + `fields.currentPassword`(비어 있음) 는 목업과 같다. 새 비밀번호가 현재와 같으면 `fields.newPassword`. 성공 뒤 「다른 기기에서는 로그아웃돼요」 안내는 서버 동작과 일치한다.
    6. 서버 문구는 모두 요청 언어(`Accept-Language`)다 — 목업이 한국어 리터럴을 쓰던 부분(`CERT_CODE_INVALID` 의 「N번 더」 포함)은 서버 `message` 를 그대로 보이면 된다.
  - **미확정/가정(5단계)**: 승인번호 유효 10분·5회 소진·쿨다운 60초·이메일 5회/IP 20회/60분(가정, 설정값), 초대 수락 시 역할의 권한 상승 재검사 없음(초대 만들 때 검사한 역할을 그대로 부여 — 그 뒤 역할 권한이 바뀌면 바뀐 대로), **루트(최고 관리자)도 비밀번호 재설정 대상**(메일함 소유 증명으로 충분하다고 본 가정 — `operator-permissions.md` 미확정 9 루트 분실 절차와 같이 확정 필요), 현재 비밀번호 오류의 별도 제한 없음, 승인번호 메일을 못 보내도 번호는 남는다(쿨다운 뒤 다시 받기), 비밀번호 변경·재설정 때 세션 종료와 동시에 들어온 로그인은 세션이 남을 수 있는 짧은 경합(비밀번호 변경 시각 기준 세션 무효화는 후속), 승인번호 요청의 감사 기록은 익명 실패 줄이 IP 한도(시간당 20)까지 쌓인다(보관 배치가 정리).
- **6단계 구현 결과(2026-10-22, 운영자 계정 보강 3건 — 서버만, 프론트 확인 필요)**: Flyway shared **`V30__operator_name_unique`**(번호는 병행 세션의 `V24~` 와 겹치지 않게 일부러 띄웠다 — 아래 「번호」). 새 API 는 없고 기존 API 의 거절 규칙·응답이 늘었다.
  1. **직접 추가 ↔ 대기 초대 충돌 방지**. `POST /api/admin/operators` 가 같은 이메일(소문자 정규화 후)의 **유효한 대기 초대**(`consumed_at IS NULL` 이고 `expires_at` 이 지나지 않음)가 있으면 **409 `OPERATOR_INVITATION_PENDING`**(`fields.email` 에도 같은 문구) 로 거절한다 — 「이미 이 이메일로 보낸 초대가 있어요. 초대를 취소한 뒤 다시 추가해 주세요.」(ko/en). 초대를 자동으로 지우지 않는다(운영자가 목록에서 취소). **만료된 대기 초대는 거절하지 않는다**(쓸 수 없는 링크 — 행은 정리 배치 `operator-invitation-cleanup` 이 만료 30일 뒤 지우고, 그동안 「초대 대기」 목록에 만료로 보일 수 있다. 그 링크로 수락하면 `INVITATION_EXPIRED` 가 먼저다). 검사 순서: 이메일 형식(400) → 이미 운영자(409 `OPERATOR_EMAIL_DUPLICATED`) → 유효한 대기 초대(409 `OPERATOR_INVITATION_PENDING`) → 이름 중복(409 `NICKNAME_TAKEN`) → 역할. **반대 방향**(`POST /api/admin/operator-invitations`)은 처음부터 같은 이메일의 기존 운영자를 `OPERATOR_EMAIL_DUPLICATED`(409)로, 유효한 기존 초대를 `INVITATION_DUPLICATED`(409)로 막는다 — 이번에 바꾼 것은 없고 짝만 맞췄다(대칭: 「이미 운영자」 ↔ 「이미 초대함」).
  2. **경합 방어**. 직접 추가·운영자 수정·초대 만들기·초대 수락·내 정보 닉네임이 **하나의 트랜잭션 어드바이저리 잠금 `7340003`**(이름 `OperatorIdentityLock`, 옛 `ProfileNicknameLock`)을 **행 잠금보다 먼저** 잡고 검사한 뒤 쓴다(잠금 순서 고정 → 교착 없음; 초대 수락은 모르는 토큰을 이 전역 잠금 전에 거른다). 유일 인덱스(이메일 `ux_operators_email`, 이름 `ux_operators_name_lower`, 대기 초대 이메일 `ux_operator_invitations_pending_email`)는 그래도 새는 경우의 마지막 방어이고 위반은 같은 409 로 바꾼다.
  3. **운영자 이름 유일(대소문자 무시)**. 모든 이름 입구가 같은 규칙이다: 운영자 직접 추가·수정(`operatorName`), 초대 수락(`nickname`), 내 정보 닉네임(`nickname`), 설치 마법사 루트(운영자 표가 빈 새 DB 라 충돌할 수 없다 — `server/api` 는 수정하지 않았다). 응답은 모두 **409 `NICKNAME_TAKEN`**(코드 하나로 통일); 운영자 추가·수정에서는 `fields.operatorName`=「이미 쓰고 있는 이름이에요. 다른 이름을 입력해 주세요.」 가 함께 온다(칸 아래에 붙일 것). 초대 수락·내 정보는 지금처럼 칸 없이 `message`(「이미 쓰고 있는 닉네임이에요 …」)뿐이다. 이름이 그대로이거나 자기 이름의 대소문자만 바꾸는 수정은 통과한다. 운영자 추가·수정의 이름은 닉네임 규칙(2~12자·문자 제한)이 아니라 기존 규칙(1~20자)을 그대로 쓴다. 비교는 DB 의 `lower()` 이고 유일 인덱스는 `lower(operator_name)` 와 같다.
  4. **마이그레이션 `V30` 의 중복 해소(기존 DB)**. 인덱스를 만들기 전에 같은 이름(`lower` 기준)이 둘 이상이면 **가장 먼저 만든 행(`created_at`, `id`)은 그대로** 두고 나머지를 `이름 2`, `이름 3` … 으로 바꾼다(공백+숫자 접미사; 다른 운영자 이름과 겹치면 숫자를 올려 빈 이름을 찾고, 20자를 넘으면 이름 앞부분을 잘라 20자에 맞춘다 — 자른 끝 공백은 지운다). 바뀐 행마다 **감사 기록 `OPERATOR_NAME_DEDUP`**(SYSTEM, 대상 = 그 운영자, `detail` = 바뀌기 전·후 이름)을 남기고 Flyway 로그에 총 건수를 찍는다. 이름이 바뀐 운영자에게 알리는 방법은 없다(감사 로그에서 찾고 운영자가 직접 알려야 한다). 개발 DB(`roboyam`)는 확인 당시 운영자 1명·중복 0건이라 영향이 없다.
  5. **로그인 이력의 접속 환경(User-Agent)**. 로그인 성공·실패 감사 기록(`LOGIN_SUCCESS`·`LOGIN_FAILURE`, 비밀번호 재설정으로 로그인되는 `LOGIN_SUCCESS` 포함) `detail.agent` 에 **원문이 아니라 요약**을 남긴다: 앞 200자로 자르고 제어문자·서식문자를 지운 뒤 정규식으로 `브라우저 / 운영체제 / 기기`(브라우저 Edge·Opera·Firefox·Chrome·Safari, OS Windows·macOS·iOS·Android·Linux, 기기 Desktop·Mobile·Tablet — 영문 고정 낱말, 버전 없음; 예 `Chrome / Windows / Desktop`). 브라우저나 OS 를 못 알아내면 **정제한 원문 앞 80글자**(이메일처럼 보이는 조각은 `(hidden)`)만 남기고, 헤더가 없거나 비었으면 칸을 만들지 않는다. `GET /api/admin/profile/login-history` 의 `agent` 가 이 값을 돌려준다(옛 기록·UA 없는 요청은 null → 화면 「알 수 없음」). 감사 로그 조회에서는 `changes` 에 `agent` 한 줄로 보인다. 로그인 잠금 중의 시도는 기존처럼 기록하지 않는다. 확인: 비밀번호·이메일 원문이 `detail`·로그에 없다.
  - **정책 가정(6단계)**: UA 요약은 IP 와 같은 감사 보관 기간(365일, 감사 보관 배치가 삭제)을 따른다 · UA 는 요청자가 꾸밀 수 있는 참고 기록이라 판정에 쓰지 않는다 · 만료된 대기 초대는 직접 추가를 막지 않는다 · 중복 이름 정리 접미사는 「공백+숫자」이고 정리는 한 번(V30)뿐이다.
  - **번호**: versioned 마이그레이션은 V23 다음 `V30` 이다(병행 개발이 `V24~` 를 쓸 수 있어 비워 두었다). Flyway 는 이미 `V30` 이 적용된 DB 에 나중에 낮은 번호(`V24~`)가 들어오면 기본 설정에서 거부하므로 **병합 때 그 사이 번호를 쓸 새 파일이 있으면 V31 이상으로 올리거나** 적용 순서를 확인한다.
  - **프론트 확인(`// REAL:` 연결 후)**: ① 운영자 추가/수정 다이얼로그가 409 `NICKNAME_TAKEN` 의 `fields.operatorName` 을 **이름 칸 아래**에 보이는지(`fields.email` 처럼 `error.fields` 를 칸에 매핑하는 기존 경로 재사용) ② 운영자 추가의 409 `OPERATOR_INVITATION_PENDING`(`fields.email` 에도 문구가 온다)이 **이메일 칸 아래**나 폼 위쪽에 보이는지 — 알 수 없는 코드라 일반 오류 토스트로만 처리되고 있지 않은지 ③ 내 정보 > 로그인 이력의 접속 환경 칸이 `Chrome / Windows / Desktop` 같은 글자를 그대로 보이는지(기기 낱말은 영문 고정) ④ 감사 로그 화면이 새 작업 `OPERATOR_NAME_DEDUP`(「운영자 이름 중복 정리」)와 로그인 기록의 `agent` 변경 한 줄을 어색하지 않게 보이는지.

  - **구조**: 이벤트 정의의 원천은 enum `AdminNotificationEvent`(shared `notification.entity`, 22개 = 발행처 있는 11 + 예약 11)이고 서버가 뜰 때 `NotificationCatalogSynchronizer` 가 `notification_events` 와 맞춘다(운영자가 바꾼 값은 유지, 사라진 이벤트·그 개인 끄기는 삭제, 필수 이벤트가 꺼져 있거나 이메일 불가 이벤트의 이메일이 켜져 있으면 규칙에 맞춤). 기동 때 모든 이벤트의 번들 키 5개(`notification.event.<코드>.name|description|recipients|title|body`, ko·en)를 확인해 **빠지면 `local`·`dev` 는 기동을 멈추고 그 밖은 ERROR 로그**. 발행기 `NotificationPublisher.publish(이벤트, NotificationContext)` 는 shared 에 있어 api 도 쓸 수 있다.
  - **발행 = 업무 트랜잭션 참여 + 알림 실패 격리**: 알림 행은 업무와 한 트랜잭션이라 업무가 롤백되면 알림도 없다(검증: 커밋 때 실패하는 트랜잭션·검증 오류 요청 모두 알림 수 불변). 수신자 계산·행 만들기는 **업무 트랜잭션 연결에 잡은 JDBC 세이브포인트** 안에서 하고 실패하면 되돌린 뒤 ERROR 로그만 남기고 0 을 돌려준다 — try-catch 만으로는 PostgreSQL 이 실패한 문장 뒤 트랜잭션 전체를 못 쓰게 해 업무 저장까지 날아가기 때문이다(검증: `admin_notifications` 에 INSERT 를 막는 트리거를 걸어도 사이트 설정·운영자 상태 변경은 200 이고 저장·감사 기록은 남음). 스프링 중첩 트랜잭션(`PROPAGATION_NESTED`)은 JPA 방언이 세이브포인트를 안 내놓아 쓰지 못했고(`NestedTransactionNotSupportedException`), 알림 행은 JPA 영속성 컨텍스트에 올리지 않고 JDBC 로 넣는다(실패한 엔티티가 업무의 다음 flush 를 깨는 일 방지). 부르기 직전 `EntityManager.flush()` 로 업무 쪽 오류가 알림 오류로 삼켜지지 않게 한다.
  - **수신자**: `SELF`(대상 운영자, 상태와 무관하게 쌓음) · `PERMISSION_HOLDERS`(권한 중 하나라도 가진 역할의 운영자 + 루트, **활성 운영자만**: 승인·잠기지 않음·만료 표시 없음·사용 중·기간 안) · `ROOT`, 맥락의 추가 수신자(초대한 운영자), `excludeActor`. 이벤트 관리에서 꺼진 이벤트·운영자가 끈 이벤트는 건너뜀(필수 이벤트는 둘 다 무시). **묶기**: `collapseSeconds` 안에 같은 수신자가 같은 이벤트·같은 `dedupeKey` 알림을 이미 받았으면 새 알림을 **만들지 않는다**(처음 것이 남음 — 기존 행을 고치지 않아 `latestId` 감지가 어긋나지 않고 시간은 처음 알림부터 센다). `sentLast30Days` 는 알림 행 수(받은 사람마다 한 건).
  - **조회**: 목록·`unread`·`summary`·`read-all` 은 `NotificationVisibility` 한 곳의 같은 거르기(발행처 있음 + 보는 권한 있음 + 내가 끄지 않음, 필수는 늘 보임)를 쓴다 — 권한을 잃으면 조회 시점에 사라지고 다시 얻으면 다시 보인다. 커서는 알림 id(최근순), `size` 기본 30·최대 100(밖이면 400 `fields.size`), 커서가 숫자가 아니면 400 `fields.cursor`. 제목·본문은 저장된 키+인자를 요청 언어로 풀고, 인자 원소는 글자 또는 `{"key","args"}`(배치 이름·「역할 추가」 문장처럼 읽을 때 풀리는 문구).
  - **이메일**: 커밋 뒤(`@TransactionalEventListener(AFTER_COMMIT)`) 별도 스레드풀(2개·대기열 200)에서 보낸다 — 이벤트의 `emailable` + 이벤트 관리의 이메일 전달 + 운영자의 `email_notification` 이 모두 참일 때만. 받는 사람의 언어 = 내 표시 형식을 쓰면 그 언어, 아니면 사이트 표시 기본 언어, 없으면 ko. 링크는 `ADMIN_URL` 기준 절대 주소(없으면 경로만). 메일 서버가 없으면 로그만. 주소·내용·예외 문구는 로그에 남기지 않는다.
  - **배치 알림 감시자**(`BatchRunWatcher`, `@Scheduled` 30초 — `roboyam.notification.batch-watch-seconds`, 서버 한 대에서 끌 수도 있음 `watcher-enabled`): 끝났는데(`finished_at`) `notified_at IS NULL` 인 줄을 `FOR UPDATE SKIP LOCKED` 로 50개씩 잡아 한 트랜잭션에서 알림 + 표시. `FAIL` → `BATCH_RUN_FAILED`(인자: 배치 이름 문구 참조·배치 키·오류 요약(실행 로그에 이미 가린 문장, 없으면 「배치 로그 확인」), 묶음 키 = 배치 키, 30분), `OK` 이고 건수>0 인 `grade-promotion` → `GRADE_PROMOTION_RUN`. 끝난 지 24시간(`batch-watch-max-age-hours`)이 넘은 줄은 알리지 않고 표시만(감시가 오래 멈췄다 돌아온 경우). 마이그레이션이 기존 줄을 채워 기동 직후 폭주가 없다.
  - **발행 연결**: 업무 서비스 12개에 호출 한 줄씩 — 상황별 문장이 갈리는 것은 `AdminNotices`(admin) 도우미를 부른다: 초대 수락(`OperatorInvitationAcceptService`) · 운영자 직접 추가·상태 변경(칸마다 한 건, 잠김/사용 중지/승인 취소/만료는 warning, 풀림 등은 info)·계정 기간 변경·역할 추가/회수(회수는 warning) (`OperatorService`) · 로그인 실패 잠금 **시작 순간 한 번**(`AdminLoginAttemptService` — `attempt.fail` 이 true 를 줄 때만, 이미 있는 이메일일 때만, 이메일 원문 대신 운영자 이름) · 역할 권한 변경(`RoleService.setPermissions` — 그 역할을 받은 운영자마다, 권한을 거두면 warning) · 비밀번호 변경·재설정 · 사이트 설정(기본 정보·로고·아이콘·링크 미리보기·표시 기본값 5개 서비스, 묶음 60초) · 등급 설정 저장(변경이 있을 때만). **역할 삭제는 발행하지 않는다**(쓰는 운영자가 있으면 삭제 자체가 409 `ROLE_IN_USE` 라 받을 사람이 없다).
  - **정리 DB 배치** `notification-cleanup`(03:50 KST, `batch_params`: `read_retention_days` 30(읽은 지)·`unread_retention_days` 90(만든 지)·`per_operator_cap` 500·`chunk_size`·`max_per_run`): ① 읽은 지 30일 ② 안 읽은 채 90일 ③ 운영자당 500건 초과(남기는 차례 = 안 읽은 것 최근순 → 읽은 것 최근순, 그래서 오래된 읽은 것부터 지우고 모자라면 오래된 안 읽은 것). 건수 0 이면 SKIP.
  - **계약서와 다른 점/가정**: ⓐ 영역 id 에 알림 전용 `security`(보안)가 있다 — `PermissionArea` 를 그대로 재사용하지 못했다(`NotificationArea`). ⓑ 이벤트마다 번들 키가 4개가 아니라 5개(수신 대상 문구 `.recipients` 추가). ⓒ 필수 이벤트에도 개인의 이메일 수신 설정(`email_notification=false`)은 적용된다(알림 메일만 끌 수 있다). ⓓ `GET /profile/notification/events` 의 `emailable` 은 「이 이벤트가 지금 이메일로 가는가」(코드가 허용 + 이벤트 관리의 이메일 전달 켜짐). ⓔ 개인 끄기 변경은 감사 `PROFILE_NOTIFICATION_UPDATE`(`event` + `before/after.muted`)로 남긴다. ⓕ 읽은 알림의 보관 30일은 **읽은 시각** 기준, 안 읽은 알림의 90일은 만든 시각 기준. ⓖ 같은 묶음 시간 안의 중복은 기존 행을 고치지 않고 새 행을 만들지 않는다. ⓗ 이벤트 코드를 모르는(카탈로그에서 사라진) 알림 행은 서랍에서 보이지 않는다(보관 정책이 지운다).
  - **프론트 `// MOCK:` → `// REAL:` 때 어긋나는 점**: ① 목록 응답이 `{items, nextCursor, unread}` 로 바뀌고 항목에 `eventCode`·`area`·`link:{path}\|null` 이 더해지며 `kind` 에 `critical` 이 있다. ② 목록과 별도로 `GET /notifications/summary`(`{unread, latestId}`)를 20초 폴링하고 `latestId` 가 바뀌면 목록을 받는다. ③ 읽음은 `POST /{id}/read`(204)·`/read-all`(204), 남의 알림·없는 알림은 404 `NOTIFICATION_NOT_FOUND`. ④ 개인 설정: `GET/PUT /profile/notification/events[/{code}]`(필수 끄기 409 `NOTIFICATION_MANDATORY`, 모르거나 권한 없는 이벤트 404 `NOTIFICATION_EVENT_NOT_FOUND`). ⑤ 이벤트 관리: `notification.read`/`notification.manage` 와 오류 `NOTIFICATION_MANDATORY`(409)·`NOTIFICATION_EVENT_NOT_READY`(409)·`fields.enabled|emailEnabled`(400). ⑥ 문구는 서버가 요청 언어로 만든다(`profile.emailNotificationHint` 는 「알림 메일만 끌 수 있고 초대·재설정 같은 시스템 메일은 끌 수 없다」로 프론트 번들에서 고친다).
- **가정**(정책 문서의 미확정 세부, 구현 때 바꿀 수 있다): 관리자 로그인 실패 5회 잠금(해제는 10분 뒤 자동, 공개 사이트 `LoginAttemptService` 방식 참고), 세션 비활동 2시간·최대 12시간·쿠키 이름 `ADMIN_SESSION`(공개 `SESSION` 과 분리), 초대 유효 72시간, 반려 사유 200자, 감사 보관 1년(보관 배치는 후속), 운영자 비밀번호 규칙은 공개 사이트 가입 규칙과 같다.
- **1단계 범위 밖**: 초대 링크를 받아 비밀번호를 정하는 화면·API(→ 5단계에서 구현), 신청서를 받는 공개 화면, 감사 로그 조회 API(→ 4단계에서 구현), 비밀번호 재설정, 회원 역할 수동 부여.
**정책의 출처**: `docs/domain/operator-permissions.md`(확정 규칙·역할 유형 표·추가 확정). 이 문서는 화면이 정한 모양과 API 후보만 적는다.

## 규칙 (화면에서 정한 것)
- **운영자 역할 유형** = 카탈로그 세부 유형 24개(id `op_<유형id>`), 영역 9개 아래. 역할 하나는 세부 유형 하나에 속하고 후보 권한은 그 유형 것만. **종합 관리** 유형은 유형 제한 없이 고르며 최고 관리자만 만들고 고친다.
- **종합 탭**의 영역별 관리자(`<영역> 관리자`, 권한 = 그 영역 전부)는 목업 시드다(카탈로그에서 계산). 서버 시드로 둘지 미정.
- **회원 역할 유형 4종**: 등급(파생, `ROLE_GRADE_<key>`) · 회원 유형(제품 고정) · 게시판 단위(매니저·스텝, 제품 고정) · 사용자 정의(운영자가 추가). 새로 만들 수 있는 것은 사용자 정의뿐.
- 공통: 권한 합집합, 권한 상승 방지(자기 권한 범위 안에서만 부여), 내장 역할 삭제 불가. 권한: 조회 `role.read`·`operator.read`·`grade.read`, 변경 `*.manage`. 감추는 것은 편의이고 막는 것은 서버다.
- **운영자 계정**: 4개 상태(승인·잠금·만료·사용)와 계정 기간. 루트(최고 관리자)는 어떤 변경도 거절. 등록 두 방식 — 생성/초대(**초대 링크**, 유효 72시간, 같은 이메일의 유효 초대는 409) · 신청 후 승인/반려(반려는 승인 대기 건만, 사유 선택 200자).
- **등급**: 순서 있는 목록 2~10단계, 첫 등급은 삭제·이동 불가, 삭제하면 소속 회원은 바로 아래 등급으로 이동. 자동 승급 조건(가입 일수·글+댓글 수) — 활동 조건은 즉시, 일수 조건은 배치(주기 미확정). 수동 상향 옵션(`CONTINUE_AUTO` 기본 / 자동 승급 중지). 기준을 낮추거나 등급을 추가·삭제하면 저장 전 영향 미리보기 후 확인(소급 승급). 등급 목록+옵션+뱃지를 **PUT 한 번**으로 저장.

## 미확정 사항
1. 사용자 정의 역할을 회원에게 수동 부여하는 화면·API.
2. 반려한 신청의 보관 방식, 반려 사유를 신청자에게 알릴지, 만료된 초대의 보관·재발송, 초대 유효기간 값(72시간은 가정).
3. 등급 일수 조건 배치의 실행 주기·시각(하루 한 번 04:30 KST 는 가정 — 운영자가 cron 으로 바꿀 수 있다), 소급 승급 시 알림·이력, 활동 수 정의(삭제·숨김 제외 여부) — `operator-permissions.md` 미확정 11.
4. 종합 탭 영역별 관리자 역할을 서버 시드로 둘지, 권한 중 화면이 아직 없는 것(`featureReady:false`)까지 줄지.
5. 운영자 로그인 세부(잠금 해제 방식, 비밀번호 재설정), 감사 보관 기간(1년은 가정), 신청 항목·승인자 권한.
6. 서버 구조: `operators` 별도 테이블·역할/권한 3표, `users.role` 의 운영자 값 제거, 관리자 서버 인증 분리(`operator-permissions.md` "이 정책이 바꾸는 현재 코드").

## 회원 상세 활동·등급 이력(서버) 구현 결과 (2026-10-22) — ⚠ 집계 정의·색인·「승급 미연결」 서술은 아래 「세션 정리 — 서버 수정 결과」 절이 대체한다
화면(`MemberDetailRolesSection`·`MemberDetailGradePointSection`)은 아직 안내문 상태이고 서버만 채웠다(프론트 연결은 다음 단계 — `// MOCK:`/null 처리 교체). `GET /api/admin/members/{id}`(권한 `member.read`, 이메일 마스킹·감사 `MEMBER_VIEW` 그대로)의 **`activity`·`gradePoint`** 두 칸을 구체 레코드로 채운다. 나머지(연락처·프로필/메모·개인 설정·동의 변경 이력·공동구매·알림함·제재/신고·휴면·포인트 내역·`statusReason` …)는 도메인 기능이 없어 여전히 null/빈 배열이다.

**마이그레이션** (shared, 번호는 다른 세션의 미커밋 `V43__menus` 와 겹치지 않게 V44·V45 를 썼다 — 합칠 때 번호를 다시 확인한다)
- `V44__member_grade_changes`: 등급 변경 이력 표. `V45__post_comment_author_indexes`: 글·댓글 작성자 부분 색인 2개.
- 반복 마이그레이션 `R__batch_15_grade_promotion.sql` 수정(승급과 같은 문장에서 이력 한 줄) — 내용이 바뀌어 기동 때 다시 적용된다.

**응답 모양** (admin-web `MemberActivity`·`MemberGradePoint` 와 필드·값이 같다. `null` 칸은 키가 그대로 나간다)
- `activity`: `postCount`·`commentCount`·`recentPostCount`·`recentCommentCount`(실제 집계) + `likesReceived`·`popularCount`·`recentLoginDays`(= 0). **탈퇴 회원은 `activity`·`gradePoint` 모두 null**(기존 축약 규칙).
- `gradePoint`: `autoPromotion`(`ACTIVE`/`PAUSED_ADMIN`/`PAUSED_SANCTION`), `next`(다음 등급 `gradeKey` + `requirements[{kind: DAYS|ACTIVITY, current, required}]`, 마지막 등급이면 null), `gradeHistory`(최근 것이 먼저 최대 50건: `changeId`·`fromGrade`(null 가능)·`toGrade`·`kind`(`AUTO`/`ADMIN`/`RESUME`)·`reason`·`actorNickname`·`changedAt`), `nicknameTicketCount`(= 0), `pointEntries`(= 빈 배열).
- 못 맞춘 칸 없음. 타입은 `MemberActivity`·`MemberGradePoint`(+`MemberGradeNext`·`MemberGradeRequirement`·`MemberGradeChange`·`MemberPointEntry`)로 `MemberDetailView` 의 `Object` 두 칸을 대체했다.

**활동 요약 집계 기준 (가정)**
- 글: 회원 글(`author_id` 있음) · `status='PUBLISHED'`(임시저장 제외) · `deleted_at IS NULL` · **`hidden_at IS NULL`(숨김은 세지 않는다)**. 댓글: 회원 댓글 · 삭제 안 됨 · 숨김 아님(그 댓글이 달린 글의 삭제·숨김 여부는 보지 않는다 — 글과 조인하면 색인만으로 끝나지 않는다). 비회원 글·댓글은 어느 회원에게도 세지 않는다.
- 최근 7일 = `created_at >= 지금 - 7일`(경계 포함, 서버 시각 기준). 글·댓글 모두 `created_at` 기준.
- `likesReceived`·`popularCount` = 0(추천·인기글 기능 없음). `recentLoginDays` = 0 — **로그인 성공은 `users.last_login_at` 하나뿐**이고 `login_attempts` 는 이메일별 실패 횟수/잠금 표라 「최근 7일 중 접속한 날」을 알 수 없다(마지막 로그인으로 0/1 을 만들면 오해를 부른다). 날짜별 접속 기록이 생기면 채운다.

**인덱스 근거 (V45)**
- `ix_posts_author (author_id, created_at DESC) WHERE author_id IS NOT NULL AND status='PUBLISHED' AND deleted_at IS NULL AND hidden_at IS NULL`, `ix_comments_author (author_id, created_at DESC) WHERE author_id IS NOT NULL AND deleted_at IS NULL AND hidden_at IS NULL`. 조회 조건이 색인 조건과 글자 그대로 같아 부분 색인을 타고, 전체 수는 색인 항목 수(index-only scan), 최근 7일은 같은 색인의 `created_at` 범위다. 삭제·임시저장·숨김·비회원 행은 색인에 들어가지 않는다.
- 두 표 모두 작성자 조건으로는 파티션 가지치기가 안 된다(글 = id 월 범위, 댓글 = post_id 해시 64) → 조각마다 색인을 한 번씩 찌른다. 글은 달마다 1조각(연 12개씩 늘어난다), 댓글은 64개 고정. 글 id(Snowflake)로 최근 구간을 좁히는 가지치기는 일부러 쓰지 않았다(임시저장했다 나중에 공개한 글처럼 id 시각과 `created_at` 이 어긋나면 누락).
- 부모 표에 만든 색인은 모든 조각에 생기고 `board_ensure_post_partitions` 가 만드는 새 조각에도 자동으로 붙는다(확인함).
- 일회용 DB 실측: 글 약 46만(조각 16개)·댓글 약 62만 건에서 많이 쓴 작성자(글 2.97만·댓글 2만) 한 명의 네 개 수를 한 문장으로 세는 데 실행 13ms(계획 23ms), 회원 상세 API 전체 약 33ms, 보통 작성자는 약 27ms. 실행계획은 데이터가 있는 모든 조각에서 `Index Only Scan`(Heap Fetches 0), 데이터 없는 미래 조각만 비어 있어 `Seq Scan`(비용 0). 새 조각이 자라는 동안 자동 분석(autovacuum) 전에는 색인을 안 탈 수도 있으나 조각 하나의 크기에 비례할 뿐이다.
- **잠금**: 일반 `CREATE INDEX` 는 만드는 동안 그 표의 쓰기를 막는다. 지금은 글·댓글 쓰기 기능이 없어 표가 비어 있어(V42 는 표만 만들었다) 즉시 끝난다. **쓰기 기능이 배포돼 데이터가 쌓인 뒤에 비슷한 색인을 더해야 하면 이 방식을 쓰지 않는다** — 부모에 `CREATE INDEX … ON ONLY`, 조각마다 `CREATE INDEX CONCURRENTLY`, `ALTER INDEX … ATTACH PARTITION` 을 트랜잭션 밖(별도 Flyway 비트랜잭션 스크립트 또는 운영 작업)에서 한다. V45 파일 머리말에 같은 지침을 적었다.
- 매우 많이 쓴 작성자(수십만 건)는 정확한 수를 세는 비용이 그 작성자 색인 항목 수에 비례한다(만 건 단위에서는 수 ms). 더 필요해지면 작성 쪽에서 증감하는 카운터 표로 옮긴다.

**등급 승급의 활동 수 판정은 연결하지 않았다 (판단)**
- 현재 동작: Java `GradePromotionService`·`GradeRepositoryQDSL` 과 DB 배치 `grade-promotion` 모두 활동 수를 0 으로 본다 → 활동 조건이 있는 등급(기본 시드의 일반·단골·베테랑 중 `min_activity>0` 인 것)은 도달 불가.
- 이유: ① DB 배치는 매일 **전체 정상 회원**을 훑으므로 회원마다 글 월 조각 + 댓글 64조각의 색인을 찔러야 한다(실측: 위 조건에서 회원 5천 명을 도는 데 약 0.7초 → 100만 명이면 일 수 분의 DB 시간이고, 조건을 영영 못 채우는 회원은 매일 다시 센다. 글 조각이 늘수록 선형으로 커진다). ② 승급 대상 판정이 Java(`promotable` QDSL·`promoteAll`·`countPromotedTo` 미리보기)와 SQL 두 곳이라 활동 수 서브쿼리를 양쪽·미리보기까지 같은 뜻으로 넣어야 하고, 등급 저장 PUT 한 번이 전체 회원 집계를 부르게 된다(요청 지연·잠금 시간 증가). ③ 글·댓글을 쓰는 기능이 아직 없어 지금 이으면 얻는 것이 없고 기본 시드 등급의 승급 동작만 바뀐다.
- 대신 **회원 상세의 `next.requirements[ACTIVITY].current`** 는 실제 글+댓글 수를 보인다 → 달성도 100% 인데도 자동 승급이 안 되는 회원이 보일 수 있다(엔진이 활동 수를 아직 0 으로 보기 때문). 화면 문구/운영 안내에서 이 차이를 알려야 한다.
- 잇는 방법(후속): 글·댓글 작성/삭제 트랜잭션이 `member_activity_counts(user_id, post_count, comment_count)` 를 증감하고, `promoteOnEvent` 가 그 값을 쓰며, SQL 배치·QDSL `promotable` 이 같은 카운터 표를 조인한다(Java `activityReachable`·SQL `c_known_activity` 제거). 그때 두 쪽이 같은 데이터에서 같은 결과를 내는지 다시 비교한다.

**등급 변경 이력 (V44)**
- 표 `member_grade_changes(id IDENTITY, user_id→users CASCADE, from_grade_key NULL, to_grade_key, kind, reason, reason_code, actor_operator_id, created_at)` + `(user_id, created_at DESC, id DESC)`. **id 는 Snowflake 가 아니라 DB 가 매긴다** — DB 배치(SQL)가 한 문장으로 수천 줄을 넣어 앱 발급기를 쓸 수 없다(가이드의 「ID 는 앱이 발급」의 예외로 적는다). 응답 `changeId` 는 문자열.
- **등급 키는 값으로 보존**(외래키 없음): 등급이 지워져도 이력이 안 지워지고 삭제도 막히지 않는다. 키는 재사용하지 않으므로(`grade_settings.next_serial`) 옛 키가 다른 등급을 가리키지 않는다. 지워진 키는 화면이 중립 뱃지 + 키 글자로 그린다(`useGradeAppearance.badgeOf` 확인함).
- **운영자**: `actor_operator_id` 에도 외래키를 두지 않는다. 응답 `actorNickname` = 자동(`AUTO`)이면 null, 운영자 현재 이름, **운영자가 지워졌으면 「삭제된 운영자」/「Deleted operator」**(요청 언어, 메시지 `member.gradeChange.actorDeleted`). null 로 두면 자동 승급처럼 보이기 때문이다. 이메일은 읽지도 내리지도 않는다.
- **사유**: 운영자가 입력한 `reason` 이 우선, 없으면 시스템 `reason_code`(지금은 `GRADE_REMOVED`)를 요청 언어로 푼다(`member.gradeChange.reason.GRADE_REMOVED`). 모르는 코드는 null.
- **kind**: `AUTO`(자동 승급) · `ADMIN`(운영자 변경, 등급 삭제로 인한 이동) · `RESUME`(자동 승급 재개). 프론트에 「등급 설정 변경」 종류가 없어 등급 삭제 이동은 `ADMIN` + 사유 코드로 표현했다.
- **기록 지점** — 모두 변경과 **같은 SQL 문장(데이터 변경 CTE)·같은 트랜잭션**이라 함께 커밋/롤백된다:
  1. DB 배치 `batch_grade_promotion`(`R__batch_15`): 올린 회원마다 `AUTO` 한 줄(덩어리 트랜잭션).
  2. Java 일괄 승급 `GradePromotionService.promoteAll` → `GradeRepositoryQDSL.promote`(네이티브 CTE로 교체. 등급 저장 PUT 의 소급 승급이 여기로 온다): `AUTO`.
  3. Java 즉시 승급 `promoteOnEvent`: 엔티티 한 줄 `AUTO`(아직 부르는 곳 없음).
  4. 등급 삭제로 인한 회원 이동 `GradeService.save` → `GradeRepositoryQDSL.moveMembers`(운영자 ID 인자 추가): `ADMIN`+`GRADE_REMOVED`+저장한 운영자. 탈퇴 회원은 이동은 하되 이력은 남기지 않는다.
  5. **운영자의 수동 등급 지정/해제·자동 승급 재개는 기능(`grade.override`) 자체가 아직 없어 기록 지점이 없다** — 기능을 만들 때 `MemberGradeChangeEntity.byOperator(...)` 로 같은 트랜잭션에서 남긴다(`ProfileEntity.changeGradeManually` 호출 옆).
  이미 있던 과거 승급은 이력이 없다(만들지 않았다). 등급 이름만 바뀌는 저장은 키가 그대로라 이력을 남기지 않는다.
- 이력 크기: 자동 승급은 올리기만 하므로 회원당 (등급 수−1)줄 이하 + 수동 변경 몇 줄 + 등급 삭제 이동. 별도 보관 배치는 두지 않았다(조회는 최근 50건만 읽는다).

**`gradePoint` 나머지 칸**
- `autoPromotion`: 정지(기간·영구) 회원 → `PAUSED_SANCTION`, `grade_manual=true` 이고 등급 옵션이 `STOP_AUTO` → `PAUSED_ADMIN`, 그 밖 `ACTIVE`(승급 판정의 대상 규칙과 같다. 정지가 우선).
- `next`: 지금 등급보다 서열이 높은 첫 등급. `DAYS.current` = 가입 후 경과 일수(상한 없음, 승급 판정과 같은 날짜 계산), `ACTIVITY.current` = 글+댓글 수. 두 줄 모두 항상 내린다(필요 값이 0 이면 프론트가 100%/달성으로 그린다). 마지막 등급이면 null — 프론트가 `nextNone` 문구로 처리한다(확인함).

**검증 (일회용 DB `rbverify_gp`, 끝나고 삭제)**
- 활동: 공개 4/댓글 3, 최근 2/2 — 임시저장·삭제·숨김·비회원 글·남의 글 제외, 7일 경계 ±1시간 확인. 탈퇴 회원 `activity`·`gradePoint` null, 정지 회원 `PAUSED_SANCTION`, 수동 상향+`STOP_AUTO` → `PAUSED_ADMIN`, 마지막 등급 `next=null`.
- 이력: 60건 중 50건·최근 먼저·같은 시각이면 번호 큰 것 먼저, 삭제된 운영자 대체 표시(ko/en), 지워진 등급 키·시스템 사유 풀이·모르는 코드 무시.
- 승급: DB 배치 `CALL batch_grade_promotion` 이 올린 회원마다 `AUTO` 이력(대상 아닌 정지·탈퇴·너무 젊은 회원은 없음, 재실행해도 늘지 않음, `STOP_AUTO` 에서 수동 회원 제외), Java 경로(등급 저장 PUT)도 같은 이력, 등급 삭제 이동이 `ADMIN`+`GRADE_REMOVED`+저장 운영자 이력을 남기고 탈퇴 회원은 제외.
- 권한: `member.read` 만 있으면 이메일 마스킹(`ac***@…`)·활동/등급 구획은 열람 가능, `member.pii` 면 원문, 권한 없는 운영자 403, 없는 회원 404.

**미해결**
- 승급 판정의 활동 수 연결(카운터 표 설계 포함) — 위 「연결하지 않았다」.
- 날짜별 접속 기록(`recentLoginDays`), 추천·인기글, 포인트 내역·닉네임 변경권.
- 숨김 글·댓글을 활동 수에 넣을지(권장 가정: 넣지 않음) — 운영 정책 확정 필요.

## 회원 상세 활동·등급 구획 프론트 연결 (2026-10-22)
`MemberDetailRolesSection`·`MemberDetailGradePointSection` 이 서버의 `activity`·`gradePoint` 실제 값을 그린다(타입은 이미 서버 응답과 같아 변경 없음). 글·댓글·최근 7일 수는 숫자, 서버가 아직 집계하지 않는 추천·인기글·최근 7일 접속일과 닉네임 변경권·포인트 내역은 0 대신 「준비 중」(`UtilMember.activityPending`), 등급 이력은 최근 5건만 보이고 「더 보기」로 펼친다(서버 최대 50건), 활동 수 조건 줄에는 「활동 수 기준 승급은 아직 적용되지 않아요」 보조 안내(`UtilMember.activityPromotionNotApplied` — 서버 승급 엔진이 활동 수를 연결하면 판정과 문구를 함께 지운다), 탈퇴 회원은 활동 요약에 전용 문구(등급·포인트 구획은 기존대로 구획 자체를 뺀다).

## 세션 정리 — 서버 수정 결과 (2026-10-22)
**바뀐 집계 정의** — 회원 활동 수(관리자 회원 상세 `activity`·즉시 승급 판정)는 공개 게시판의 상태 모델을 쓴다. 한 곳(shared `com.community.member.repository.master.MemberActivityRepository`)에 두고 admin 회원 상세와 api 즉시 승급이 같이 쓴다.
- 글: 회원 글 · `PUBLISHED` · `deleted_at IS NULL` · 예약 삭제 시각 전(`delete_scheduled_at IS NULL OR > now`) · 지금 숨김 아님(`hidden_at IS NULL OR (hidden_until IS NOT NULL AND hidden_until <= now)` — 임시조치가 끝나면 다시 센다). `PostEntity#isGoneAt`·`#isHiddenAt`, `PostRepositoryQDSL#alive`·`#notHidden` 과 같은 뜻.
- 댓글: 회원 댓글 · 지우지 않음 · 지금 숨김 아님(같은 규칙, 댓글 칸 기준, 글의 상태는 보지 않는다).
- 최근 7일 = `id >= floorIdAt(지금-7일) AND created_at >= 지금-7일`. `activity.likesReceived` = 위 기준으로 보이는 글·댓글의 `like_count` 합(이전에는 0).
- 회원 상세 `reports`(이전 null) = `{receivedCount, actionedCount, filedCount}` — 받은 신고(`reports.target_author_id`), 그중 `status='ACCEPTED'`, 이 회원이 한 신고(`reporter_id`). 탈퇴 회원은 `activity`·`reports`·`gradePoint` 모두 null. **신고 표에 남은 것만 센다 — 보유기간 배치(`board-privacy-retention` 신고 기록 축)가 오래된 신고를 지우면 수가 줄어든다.** 신고 처리 기능이 아직 없어 `actionedCount` 는 지금 늘 0.

- `V48__member_activity_report_indexes`: V45 의 두 작성자 부분 색인 DROP(새 정의는 `hidden_at IS NULL` 조건과 같지 않아 그 색인을 못 타고, V46 `ix_*_author_recent` 와 겹쳐 쓰기 비용만 늘린다) + `ix_reports_target_author (target_author_id, status) WHERE target_author_id IS NOT NULL`.

- 활동 집계는 V46 의 `(author_id, id DESC) WHERE author_id IS NOT NULL` 색인을 탄다. 보임 판정은 지금 시각과 비교해 색인 조건에 못 넣으므로 행을 읽어 거른다. 일회용 DB 실측(글 33만·댓글 22만, 글 조각 10개): 글 3만·댓글 2만 작성자의 요약 한 문장 19.5ms(캐시 상태), 보통 작성자 2.2ms, 회원 상세 API 전체 54~78ms. 큰 작성자의 행이 heap 에 몰려 있는 시험 데이터라 실제(글이 여러 페이지에 흩어짐)·캐시 밖에서는 더 느릴 수 있다 — 그때는 카운터 표로 옮긴다.

**즉시 승급 연결 범위** — api 글쓰기(`PostWriteService#create`)·댓글쓰기(`CommentService#create`)가 회원 글이면 **저장 커밋 뒤 별도 트랜잭션**으로 `GradePromotionService#promoteOnActivity` → `promoteOnEvent` 를 부른다(`WriterPromotion`, 실패는 WARN 로그만 — 글·댓글은 201 그대로). 일수 조건을 채운 상위 등급이 없으면 세지 않고, 있으면 그 등급들의 최대 `min_activity` 까지만 센다(`countUpTo` — `UNION ALL` + `LIMIT`, 실측 0.2~0.5ms). 올릴 때 프로필 행을 잠가 같은 회원의 동시 승급을 줄 세운다. 이력은 `member_grade_changes` kind `AUTO`. 응답의 작성자 등급 뱃지는 승급 전 값이다(승급이 커밋 뒤라서).
- **일괄 경로는 여전히 활동 수를 보지 않는다**(`KNOWN_ACTIVITY = 0` — 등급 저장 PUT 의 미리보기·소급 승급, DB 배치 `grade-promotion`). 그래서 활동 조건을 이미 채웠거나 기준을 낮춰 채우게 된 회원, 일수가 나중에 차는 회원은 **다음 글·댓글 때** 올라간다. 글·댓글을 지우거나 숨겨도 등급은 내려가지 않는다(올리기만).

**미해결**
1. 일괄 경로의 활동 수(작성 쪽에서 증감하는 카운터 표 → 배치·미리보기·QDSL 이 같은 값을 보게).
2. 활동이 없는 회원이 일수만 차서 활동 조건 등급에 닿는 경우는 다음 글·댓글까지 승급이 늦다(1과 같이 해결).
3. 큰 작성자 요약의 비용(행 수에 비례) — 회원 상세가 느려지면 카운터 표.
